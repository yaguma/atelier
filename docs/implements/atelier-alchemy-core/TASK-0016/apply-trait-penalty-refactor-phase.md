## 1. リファクタリング方針

Greenフェーズの実装はアルゴリズム7ステップと1:1対応しており、ロジック自体に明確な改善点はなかった。そのため**機能的な変更は一切行わず**、コメントの構造化・強化のみを実施した。

セルフレビューで以下3点が、Greenフェーズのコメントでは触れられてはいたものの、後続実装者への警告として弱いと判断した。

1. 2026-07-09のゲームデザインレビューで確定した仕様（支配戦略の抜け穴を塞ぐための品質スコア直接減算）であること、および旧設計（枠数ベースの食い合い）に戻さないよう注意喚起する記述
2. 触媒（SUPPORT）複数投入時の加算モデルが暫定実装であることの申し送りコメント
3. round()の丸め方式がTASK-0013から続く設計文書間の不整合への暫定対応であることの明示

`calculate_base_quality`側で既に採用されている「⚠️ 設計判断」形式（TASK-0013リファクタで導入）に倣い、同じ書式で3点を明文化することで、ファイル内のコメントスタイルの一貫性も確保した。

## 2. 改善内容

### 改善1: 「⚠️ 設計判断1」— 支配戦略対策の経緯明示・回帰禁止の注意喚起

- 【改善前】: 関数コメント冒頭に1文で「2026-07-09確定仕様を数式レベルで維持し、旧版に戻さない」と記載のみ
- 【改善後】: 独立した「⚠️ 設計判断1」ブロックとして、(a) 旧版の具体的な問題（1素材が複数特性を同時保有し品質・特性・貢献度・報酬を無条件に両取りできる支配戦略の抜け穴）、(b) 新版が採用する数式（品質スコアへの直接減算）、(c) 🚨 マーク付きで「枠数ベースの排他選択に戻すと抜け穴が再発する」という明示的な回帰禁止警告を記載
- 併せて、関数本体のpenalty_count加算部分（else節）にも「【回帰防止】」インラインコメントを追加し、コード側でも同じ注意を再掲した
- 🔵 信頼性レベル: apply-trait-penalty-requirements.md §1・REQ-111/REQ-112に基づく（要件定義書の記述をそのまま反映）

### 改善2: 「⚠️ 設計判断2」— SUPPORT複数投入時の加算モデルが暫定実装であることの明示

- 【改善前】: 上限クランプのコメントに🟡マークのみ付与、暫定性の明記なし
- 【改善後】: 「⚠️ 設計判断2」ブロックで、REQ-108本文がSUPPORT複数投入時の挙動を明記していないこと、本実装が「件数分の単純加算モデル」を暫定採用していることを明示。📝マーク付きで「バランス調整フェーズでの再検討が必要な可能性がある」という申し送りを記載
- 関数本体のSUPPORT分岐（if節）にも「【暫定実装】」インラインコメントを追加
- 🟡 信頼性レベル: 元資料に複数投入時の挙動明記なし。単純加算モデルは妥当な推測にとどまる

### 改善3: 「⚠️ 設計判断3」— round()丸め方式がTASK-0013由来の設計文書不整合への暫定対応であることの明示

- 【改善前】: 丸め処理直前のコメントに1行で「暫定確定方式」と記載
- 【改善後】: 「⚠️ 設計判断3」ブロックで、architecture.md（int想定シグネチャ）とacceptance-criteria.md（非整数期待値）の不整合がTASK-0013時点から続いていること、本タスクで変換責務と丸め方式を確定させた経緯を明示。📝マーク付きで「四捨五入以外の方式が正式決定された場合はTC-16-B03と合わせて見直す」という申し送りを記載
- 関数本体のround()呼び出し直前コメントに「【丸め方式・暫定対応】」と明記し、設計判断3への参照を追加

### その他

- コメント冒頭の【改善内容】欄に、Refactorフェーズでの変更範囲（機能変更なし、コメント強化のみ）を明記した

## 3. セキュリティレビュー

- 本関数は純粋関数（外部入力I/O・DB・ネットワークアクセスなし）であり、XSS/SQLインジェクション/CSRF等の一般的な脆弱性は該当しない
- 入力値（`base_quality`, `activated_traits`）はいずれもGodotの型システムにより型が保証されており、実行時の型混入リスクは低い
- 下限・上限クランプにより、`MaterialInstance.Quality`の値域（1〜5）を超える不正なenum値が生成されるリスクは排除されている
- 重大なセキュリティ脆弱性は発見されなかった
