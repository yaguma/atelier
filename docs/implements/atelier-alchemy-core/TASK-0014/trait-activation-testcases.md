## 対象関数シグネチャ

```gdscript
class_name TraitActivation
extends RefCounted

static func resolve_activated_traits(
    materials: Array[MaterialInstance],
    reveal_level: int,
    trait_definitions: Dictionary,  # StringName(trait id) -> TraitDefinition
) -> Array[TraitDefinition]:
```

- **入力1** `materials`: 投入素材配列。各要素は `traits: Array[StringName]`（特性タグID配列）を持つ
- **入力2** `reveal_level`: 段階的開示レベル（`0`=Gランク相当, `>=1`=Eランク以降）
- **入力3** `trait_definitions`: `StringName`(trait id) → `TraitDefinition` のマスターデータ辞書
- **出力** `Array[TraitDefinition]`: 発現候補の特性定義配列（該当なしは空配列）

## 1. 正常系テストケース（基本的な動作）

### TC-101-02: 同一特性2個＋無特性2個で特性が発現候補になる

- **テスト名**: 同一特性タグ2個の投入で特性が発現候補に含まれる
  - **何をテストするか**: 同一特性タグを2個持つ素材構成で、その特性が発現候補として返ること
  - **期待される動作**: 出現回数が閾値(2)を満たす特性のみが `TraitDefinition` として返る
- **入力値**: `materials = [聖, 聖, 無特性, 無特性]`, `reveal_level = 1`, `trait_defs`
  - **入力データの意味**: 「聖」の出現回数=2（発現）、無特性素材=2（発現に寄与しない）を代表する構成
- **期待される結果**: 戻り値 `size() == 1`、要素の `id == &"holy"`
  - **期待結果の理由**: REQ-106「2個以上で発現」を満たすタグは「聖」のみ
- **テストの目的**: 閾値発現の基本動作（2個で発現）を確認
  - **確認ポイント**: 返る件数と、返る `TraitDefinition.id` が正しいこと
- 🔵 acceptance-criteria.md TC-101-02 / REQ-106 に明記

### TC-121-02: Eランク（reveal_level=1）で貢献度系特性が発現する

- **テスト名**: reveal_level=1 で貢献度系（CONTRIBUTION）特性が解禁され発現する
  - **何をテストするか**: `reveal_level >= 1` のとき貢献度系特性が候補に残ること
  - **期待される動作**: 段階的開示フィルタを通過し、閾値を満たした貢献度系特性が返る
- **入力値**: `materials = [聖, 聖]`, `reveal_level = 1`, `trait_defs`
  - **入力データの意味**: 貢献度系「聖」を閾値ちょうど満たす最小構成
- **期待される結果**: 「聖」が発現候補に含まれる（`size() >= 1` かつ `id == &"holy"` を含む）
  - **期待結果の理由**: REQ-122「Eランク以降で貢献度系・報酬系が解禁」
- **テストの目的**: `reveal_level=1` で貢献度系が解禁されることを確認
  - **確認ポイント**: `reveal_level=0`（TC-121-01）との対比で解禁が効いていること
- 🔵 acceptance-criteria.md TC-121-02 / REQ-122 に明記

### TC-101-06: 同一系統内で複数特性が同時発現候補になる

- **テスト名**: 同一系統内で閾値を満たす複数特性がすべて同時発現する
  - **何をテストするか**: 系統排他ではなく、閾値を満たした複数特性がすべて返ること
  - **期待される動作**: 「聖」「浄」がともに閾値を満たすとき両方返る（系統内は排他しない）
- **入力値**: `materials = [聖, 聖, 浄, 浄]`, `reveal_level = 1`, `trait_defs`
  - **入力データの意味**: 貢献度系の異なる2特性がそれぞれ2個ずつの投入枠4枠構成
- **期待される結果**: 戻り値 `size() == 2`、`id` 集合が `{&"holy", &"cleanse"}` に一致
  - **期待結果の理由**: REQ-112「同一系統内で閾値を満たす特性はすべて発現」。系統をまたぐ排他(REQ-115)は TASK-0015 の責務で本関数は行わない
- **テストの目的**: 系統内複数同時発現（排他しない）を確認
  - **確認ポイント**: 件数が2であること、順序に依存せず両IDが含まれること
- 🔵 acceptance-criteria.md TC-101-06 / REQ-112 に明記

## 2. 異常系テストケース（不発・退化入力のハンドリング）

> 本関数は純粋関数であり例外を投げない設計。ここでは「発現しない／空配列を返すべき」退化入力を異常系として扱う。

### TC-101-03: 同一特性1個のみでは不発になる

- **テスト名**: 同一特性が1個のみのとき発現しない（空配列）
  - **エラーケースの概要**: 閾値(2)未満の出現回数では発現候補に含めてはならない
  - **エラー処理の重要性**: 誤って1個で発現するとゲームの戦略性（2個揃える工夫）が崩れる
- **入力値**: `materials = [聖, 無特性, 無特性, 無特性]`, `reveal_level = 1`, `trait_defs`
  - **不正な理由**: 「聖」の出現回数=1 で閾値未満。発現条件を満たさない
  - **実際の発生シナリオ**: プレイヤーが特性素材を1個しか投入しなかった通常プレイ
- **期待される結果**: 戻り値が空配列（`size() == 0`）
  - **エラーメッセージの内容**: 例外ではなく空配列で「発現なし」を表現する
  - **システムの安全性**: 閾値未満を確実に除外し、後続処理（TASK-0015/0018）に誤候補を渡さない
- **テストの目的**: 閾値未満での不発（1個では発現しない）を確認
  - **品質保証の観点**: REQ-106 の下限条件を守ることでバランスの根幹を保証
- 🔵 acceptance-criteria.md TC-101-03 / REQ-106「1個のみでは不発」に明記

### TC-121-01: Gランク（reveal_level=0）では特性が一切発現しない

- **テスト名**: reveal_level=0 のとき閾値を満たしても発現しない
  - **エラーケースの概要**: 段階的開示レベル0では、どんな構成でも特性を発現させてはならない
  - **エラー処理の重要性**: Gランクは「品質のみで評価」する設計。特性が漏れると初期難易度設計が崩れる
- **入力値**: `materials = [聖, 聖]`（閾値を満たす構成）, `reveal_level = 0`, `trait_defs`
  - **不正な理由**: `reveal_level=0` では特性系がすべて未解禁
  - **実際の発生シナリオ**: Gランクのプレイヤーが特性を持つ素材を2個以上投入した場合
- **期待される結果**: 戻り値が空配列（`size() == 0`）
  - **エラーメッセージの内容**: 空配列で「非開示」を表現
  - **システムの安全性**: reveal_level フィルタが閾値判定より最優先で効くこと
- **テストの目的**: `reveal_level=0` の最優先フィルタを確認
  - **品質保証の観点**: REQ-121「Gランクでは特性が一切発現しない」を保証
- 🔵 acceptance-criteria.md TC-121-01 / REQ-121 に明記

### TC-121-E01: 未解禁特性が候補に紛れ込んでも発現しない（二重の安全策）

- **テスト名**: reveal_level=0 なら入手制限漏れの特性素材があっても発現しない
  - **エラーケースの概要**: 庭・ショップ側の入手制限が万一漏れ、本来入手不可の特性付き素材が投入枠に存在するケース
  - **エラー処理の重要性**: UI表示制御だけに依存しない「二重の安全策」（architecture.md）をロジック層で担保する
- **入力値**: `reveal_level = 0` の状態で、閾値を満たす特性付き素材（例: `[聖, 聖, 浄, 浄]`）を投入, `trait_defs`
  - **不正な理由**: Gランクでは本来これらの特性素材を入手できないはず。想定外の混入
  - **実際の発生シナリオ**: garden/workshop（Phase外）の選択肢非表示バグで特性素材が入手された場合
- **期待される結果**: どの特性であっても戻り値が空配列（`size() == 0`）
  - **エラーメッセージの内容**: 空配列で「非開示のため一切発現なし」を表現
  - **システムの安全性**: 入手制限が漏れても調合ロジック側で二重に防止できることを保証
- **テストの目的**: reveal_level フィルタが最優先されることの安全網検証
  - **品質保証の観点**: TC-121-01 の一般化。入手制御バグへの耐性を保証
- 🟡 architecture.md「非機能要件の実現方法／ユーザビリティ（二重の安全策）」より。TC-121-E01本体（庭・ショップの非表示）はPhase 3スコープ外だが、TraitActivation側の安全網として検証

### TC-101-EMPTY: 空の素材配列で空配列を返す（退化入力）

- **テスト名**: 素材が空配列のとき空配列を返す
  - **エラーケースの概要**: 投入素材が1個もない退化入力
  - **エラー処理の重要性**: 集計対象ゼロで例外を投げず安全に空配列を返す必要がある
- **入力値**: `materials = []`, `reveal_level = 1`, `trait_defs`
  - **不正な理由**: 通常は投入枠分の素材があるが、呼び出し側の状態次第で空になりうる
  - **実際の発生シナリオ**: 調合前の初期状態や、素材未選択での誤呼び出し
- **期待される結果**: 戻り値が空配列（`size() == 0`）、例外を投げない
  - **システムの安全性**: 空入力でクラッシュせず決定論的に空を返す
- **テストの目的**: 退化入力（空配列）での堅牢性を確認
  - **品質保証の観点**: 要件定義「空配列可」（入力仕様）を保証
- 🔵 要件定義書「入力パラメータ: `materials` … 空配列可」に明記

### TC-101-NOTRAIT: 全て無特性素材のとき空配列を返す

- **テスト名**: どの素材も特性を持たないとき空配列を返す
  - **エラーケースの概要**: `traits` がすべて空配列の素材のみの構成

  - **不正な理由**: 特性タグが1つも存在せず発現候補が生じない
  - **実際の発生シナリオ**: 特性を持たない基礎素材だけで調合するプレイ
- **期待される結果**: 戻り値が空配列（`size() == 0`）
  - **システムの安全性**: 発現なしを空配列で正しく表現
- **テストの目的**: 特性ゼロ構成での不発を確認

## 3. 境界値テストケース（閾値・開示レベルの境界）

### TC-101-B01: 同一特性がちょうど2個の境界値で発現する

- **テスト名**: 出現回数がちょうど閾値(2)のとき発現側に倒れる
  - **境界値の意味**: 2 は「不発(1) / 発現(2)」を分ける発現閾値そのもの
  - **境界値での動作保証**: 閾値ちょうどが発現側に含まれること（`>=` であり `>` ではない）
- **入力値**: `materials = [癒, 癒, 無特性, 無特性]`, `reveal_level = 1`, `trait_defs`
  - **境界値選択の根拠**: 出現回数=2 は REQ-106 の発現下限。1個(TC-101-03)との対比で境界を確定する
  - **実際の使用場面**: プレイヤーが最小限（2個）で特性発現を狙う典型構成
- **期待される結果**: 「癒」が発現候補に含まれる（`size() >= 1` かつ `id == &"heal"` を含む）
  - **境界での正確性**: 閾値比較が `count >= 2` で実装されていること
  - **一貫した動作**: 1個=不発 / 2個=発現 が一貫すること
- **テストの目的**: 発現閾値の境界（発現側に倒れる）を確認
  - **堅牢性の確認**: オフバイワン（`> 2` 誤実装）を排除
- 🔵 acceptance-criteria.md TC-101-B01 / EDGE-101 に明記

### TC-121-B02: reveal_level の境界（0=不発 / 1=発現）

- **テスト名**: reveal_level が 0→1 の境界で発現有無が切り替わる
  - **境界値の意味**: `reveal_level` は 0（非開示）と 1（開示）を分ける開示境界
  - **境界値での動作保証**: 同一素材構成で level=0 は空、level=1 は発現、と切り替わること
- **入力値**: 同一構成 `materials = [聖, 聖]` に対し `reveal_level = 0` と `reveal_level = 1` の2通り, `trait_defs`
  - **境界値選択の根拠**: 開示フィルタの境界（0/1）を1テストで対比検証する
  - **実際の使用場面**: G→E ランク昇格時に特性が解禁される遷移
- **期待される結果**: `level=0` → `size() == 0`、`level=1` → `size() == 1`（`&"holy"` を含む）
  - **境界での正確性**: フィルタ条件が `reveal_level >= 1` で解禁されること
  - **一貫した動作**: 境界の内外で結果が一貫すること
- **テストの目的**: 開示レベル境界での切り替わりを確認
  - **堅牢性の確認**: TC-121-01 と TC-121-02 の対を1ケースで補強
- 🔵 REQ-121 / REQ-122 の境界。TC-121-01・02 を対比した妥当な境界化

### TC-123-B03: reveal_level>=2（Dランク暫定）は level=1 と同じ扱い

- **テスト名**: reveal_level=2 が現状 level=1 と同一結果になる（暫定実装）

  - **実際の使用場面**: Dランク到達時。REQ-123確定までの暫定挙動
- **期待される結果**: 「聖」が発現候補に含まれる（`size() == 1`、level=1 と同一結果）
  - **境界での正確性**: level>=2 で例外や欠落を起こさないこと
  - **一貫した動作**: level=1 と level=2 の結果が一致すること
- **テストの目的**: REQ-123 暫定実装（level>=2 は level>=1 相当）の挙動固定
  - **堅牢性の確認**: 将来 REQ-123 確定時にこのテストが変更点の目印になる（申し送り）
