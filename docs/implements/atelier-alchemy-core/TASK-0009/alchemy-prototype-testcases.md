## 対象と方針

- **TDD主対象（Functional Core）**: 純粋関数 `PrototypeAlchemyResolver.resolve(materials)`
  （`atelier-godot/features/prototype/logic/prototype_alchemy_resolver.gd`）
- **動作確認対象（Imperative Shell）**: UI層 `alchemy_prototype.gd` / `alchemy_prototype.tscn`
  （TC7。純粋関数テストでは扱えないため、シーンレベルテストまたは手動確認とする）
- **テスト配置**: `atelier-godot/tests/unit/features/prototype_alchemy_resolver_test.gd`（GUT）
- **既存パターン準拠**: `atelier-godot/tests/unit/features/rng_service_test.gd` の GUT 記法（`extends GutTest`, `assert_eq` 等）

### `resolve` の入出力（要件定義書 2.1 より）

- **入力**: `materials: Array`（各要素は `Dictionary`。`quality: int`（D=1〜S=5）, `traits: Array[StringName]`）
- **出力**: `Dictionary`
  - `quality: int` — 最終品質スコア（1〜5、D=1を下回らない）
  - `traits: Array` — 発現特性タグIDの配列（同一タグ2個以上）
  - `success: bool` — 調合成立可否（空投入時 `false`）

### 計算仕様（プロトタイプ簡易ロジック）

1. 基礎品質 = 投入素材の `quality` 平均（端数**切り捨て** / int除算）
2. 特性発現 = 投入枠内で同一特性タグが**2個以上**で発現（1個は不発）
3. 最終品質 = 基礎品質 − 発現特性数（1個につき1段減算、ただし**D=1を下回らない**）
4. スコープ外（省略）: REQ-112（同系統複数特性の加算ペナルティ）, REQ-115（貢献度系/報酬系の排他制御）

## 1. 正常系テストケース

### TC1: 基礎品質の平均値計算 🟡

- **テスト名**: `test_基礎品質の平均値計算`
  - **何をテストするか**: 特性が発現しない素材2個を投入したとき、基礎品質が各 `quality` の平均値として算出されること
  - **期待される動作**: 品質B(3)とD(1)の平均 = (3+1)/2 = 2 が最終品質として返る（特性発現がないためペナルティなし）
- **入力値**: `[{"quality": 3, "traits": []}, {"quality": 1, "traits": []}]`
  - **入力データの意味**: 品質スコアの平均計算のみを純粋に検証するため、特性タグを持たない（発現しない）素材を選定。note.md のテストテンプレートに準拠
- **期待される結果**: `result["quality"] == 2`、`result["traits"] == []`、`result["success"] == true`
  - **期待結果の理由**: (3+1)/2 = 2。特性が1つも2個以上揃わないため発現なし＝品質ペナルティなし
- **テストの目的**: 基礎品質計算ロジック（平均）の正当性確認
  - **確認ポイント**: 平均値が正しく、特性なしの場合にペナルティが発生しないこと
- 🟡 信頼性: REQ-105を簡略化したプロトタイプ専用ロジックのテスト（TASK-0009.md テストケース1準拠）

### TC2: 特性の閾値発現（ちょうど2個） 🔵

- **テスト名**: `test_特性の閾値発現_同一タグ2個で発現`
  - **何をテストするか**: 同一特性タグを持つ素材がちょうど2個投入されたとき、その特性が完成品に発現すること
  - **期待される動作**: `contribution_holy` を2個含むため、`result["traits"]` に `contribution_holy` が含まれる
- **入力値**: `[{"quality": 1, "traits": [&"contribution_holy"]}, {"quality": 2, "traits": [&"contribution_holy"]}]`
  - **入力データの意味**: TASK-0008の `holy_herb`(D, contribution_holy) と `holy_herb_two`(C, contribution_holy) 相当。閾値ちょうど（2個）を再現
- **期待される結果**: `result["traits"].has(&"contribution_holy") == true`、`result["success"] == true`
  - **期待結果の理由**: REQ-106「同一特性2個以上で発現」、EDGE-101「閾値ちょうどで発現させる」
- **テストの目的**: 特性発現の閾値判定（境界＝2個）の正当性確認
  - **確認ポイント**: 「2個以上」の下限（＝2個）で確実に発現すること（off-by-oneで3個以上のみ発現になっていないか）
- 🔵 信頼性: REQ-106, EDGE-101に明記（TASK-0009.md テストケース2準拠）

### TC3: 特性1個のみでは不発 🔵

- **テスト名**: `test_特性1個のみでは不発`
  - **何をテストするか**: ある特性タグを持つ素材が1個だけの場合、その特性が発現しないこと
  - **期待される動作**: `contribution_holy` は1個のみのため発現せず、`result["traits"]` に含まれない
- **入力値**: `[{"quality": 1, "traits": [&"contribution_holy"]}, {"quality": 5, "traits": []}]`
  - **入力データの意味**: `holy_herb`(D, contribution_holy) 1個 + `pure_crystal`(S, 特性なし) 1個。同一タグが1個しかない状態
- **期待される結果**: `result["traits"].has(&"contribution_holy") == false`、`result["traits"] == []`
  - **期待結果の理由**: REQ-106「1個のみでは不発」
- **テストの目的**: 発現閾値未満（1個）で発現しないことの確認
  - **確認ポイント**: 閾値の下側（1個）で発現しないこと。TC2とペアで境界（1個=不発 / 2個=発現）を挟む
- 🔵 信頼性: REQ-106に明記（TASK-0009.md テストケース3準拠）

### TC4: 特性発現による品質ペナルティ 🟡

- **テスト名**: `test_特性発現による品質ペナルティ`
  - **何をテストするか**: 基礎品質B(3)で特性が1個発現する組み合わせにおいて、最終品質が1段階減算されC(2)になること
  - **期待される動作**: 基礎品質 (3+3)/2 = 3、`reward_gold` が2個で発現 → 3 - 1 = 2
- **入力値**: `[{"quality": 3, "traits": [&"reward_gold"]}, {"quality": 3, "traits": [&"reward_gold"]}]`
  - **入力データの意味**: 基礎品質3かつ特性1個発現を同時に成立させるため、品質B(3)・同一特性 `reward_gold` を2個投入
- **期待される結果**: `result["quality"] == 2`、`result["traits"].has(&"reward_gold") == true`
  - **期待結果の理由**: REQ-111簡略版「発現特性1個につき品質1段階減算」。3 - 1 = 2（C相当）
- **テストの目的**: 特性発現に伴う品質ペナルティ計算の正当性確認
  - **確認ポイント**: 発現数（1）と減算量（1）が一致すること。基礎品質計算とペナルティ減算の合成が正しいこと
- 🟡 信頼性: REQ-111を簡略化した適用（TASK-0009.md テストケース4準拠）

### TC7: 素材入手ボタンの即時反映（UIテスト） 🔵

- **テスト名**: `test_素材入手ボタンの即時反映`（シーンレベルテスト または 手動確認チェックリスト）

- **入力値**: 素材入手ボタンのクリックイベント（例: `pure_crystal` 入手ボタン）
  - **入力データの意味**: REQ-502「素材はボタン操作で即時入手（庭・時間経過なし）」の検証。非同期・成熟待ち等が介在しないことを確認

### TC11: 異なる系統の特性が各2個で同時発現 🟡

- **テスト名**: `test_異なる系統の特性が各2個で同時発現`
  - **何をテストするか**: 貢献度系・報酬系それぞれ2個ずつ投入したとき、両特性が独立して発現し、発現数に応じて品質が減算されること
  - **期待される動作**: `contribution_holy`×2 と `reward_gold`×2 → 両方発現（発現数2）。基礎品質からの減算量は2
- **入力値**: `[{"quality": 4, "traits": [&"contribution_holy"]}, {"quality": 4, "traits": [&"contribution_holy"]}, {"quality": 4, "traits": [&"reward_gold"]}, {"quality": 4, "traits": [&"reward_gold"]}]`
  - **入力データの意味**: 4枠を使い、2種類の特性タグが各々閾値（2個）に達する構成。基礎品質は全て4で平均4
- **期待される結果**: `result["traits"]` が `contribution_holy` と `reward_gold` の両方を含む（順不同、要素数2）、`result["quality"] == 2`（4 - 発現数2）
  - **期待結果の理由**: REQ-106をタグ単位で独立適用。REQ-115（排他制御）はスコープ外のため両系統が同時発現してよい
- **テストの目的**: 複数の異なる特性タグが独立してカウント・発現・減算されることの確認
  - **確認ポイント**: タグごとの独立集計が正しいこと。スコープ外のREQ-115排他制御が誤って混入していないこと（＝両系統が発現する）
- 🟡 信頼性: REQ-106のタグ単位独立判定からの妥当な推測。REQ-115スコープ外の明示的な確認を兼ねる

### TC6: 投入枠が空の場合の調合拒否 🟡

- **テスト名**: `test_投入枠が空の場合の調合拒否`
  - **エラーケースの概要**: 投入枠に素材が1つも配置されていない状態で調合を実行しようとするケース
  - **エラー処理の重要性**: 不正な状態（0素材）で品質計算（0除算等）を走らせず、調合を成立させないことでシステムの安全性とロジック整合性を保つ
- **入力値**: `[]`（空配列）
  - **不正な理由**: 投入素材が0個では基礎品質の平均計算（分母0）が定義できず、完成品を生成できない
  - **実際の発生シナリオ**: プレイヤーが素材を配置せずに調合ボタンを押した場合
- **期待される結果**: `result["success"] == false`、完成品（quality/traits）は生成・確定されない（0除算エラーやクラッシュを起こさない）
  - **エラーメッセージの内容**: プロトタイプでは大仰なダイアログは出さない。`success: false` を返す、またはUI側でボタン非活性化/押下無視
  - **システムの安全性**: 0除算を回避し、呼び出し側が `success` を見て安全に分岐できること
- **テストの目的**: EDGE-001「空投入では調合を成立させない」のエラーハンドリング確認
  - **品質保証の観点**: 境界（0素材）での防御的処理により、UI層の不正操作からロジックを保護する
- 🟡 信頼性: EDGE-001からの適用。`success: false` 表現は要件定義書2.1の妥当な推測（TASK-0009.md テストケース6準拠）

## 3. 境界値テストケース

### TC5: 最終品質はDを下回らない（境界値） 🔵

- **テスト名**: `test_最終品質はDを下回らない`
  - **境界値の意味**: 品質スコアの下限 D=1。ペナルティ減算がこの下限を突き抜けないことを保証する境界
  - **境界値での動作保証**: 基礎品質が既に最低（D=1）で、さらに特性ペナルティが乗る極端条件での下限クランプ
- **入力値**: `[{"quality": 1, "traits": [&"reward_gold"]}, {"quality": 1, "traits": [&"reward_gold"]}]`
  - **境界値選択の根拠**: 基礎品質 (1+1)/2 = 1（D）で `reward_gold` が2個発現 → 1 - 1 = 0 となるが、D=1未満は許されない
  - **実際の使用場面**: 低品質素材ばかりで特性が発現する組み合わせを投入したケース
- **期待される結果**: `result["quality"] == 1`（0や負値にならずD=1でクランプ）
  - **境界での正確性**: 減算結果が下限を下回る場合に 1 へ正規化される
  - **一貫した動作**: 下限より上（TC4=2）と下限（TC5=1）で計算式が一貫していること
- **テストの目的**: REQ-111「最終品質はD=1を下回ってはならない」の境界確認
  - **堅牢性の確認**: 極端な低品質＋ペナルティでも品質が破綻しない
- 🔵 信頼性: REQ-111, EDGE-102に明記（TASK-0009.md テストケース5準拠）

### TC8: 基礎品質平均の端数切り捨て 🟡

- **テスト名**: `test_基礎品質平均の端数切り捨て`
  - **境界値の意味**: 平均が割り切れない（小数を含む）ケース。切り捨て仕様の境界動作を確認
  - **境界値での動作保証**: 端数処理が四捨五入ではなく切り捨て（int除算）であることを保証
- **入力値**: `[{"quality": 5, "traits": []}, {"quality": 5, "traits": []}, {"quality": 2, "traits": []}, {"quality": 3, "traits": []}]`
  - **境界値選択の根拠**: (5+5+2+3)/4 = 15/4 = 3.75 と、小数点以下 .75 が出る構成を選定。四捨五入なら4、切り捨てなら3となり両者の差が明確に判別できる。特性は発現させずペナルティの影響を排除
  - **実際の使用場面**: 4枠に品質バラバラの素材を入れて平均が小数になるケース（実運用で頻出）
- **期待される結果**: `result["quality"] == 3`（3.75の切り捨て。四捨五入なら4になるが、切り捨て仕様のため3）
  - **境界での正確性**: 小数点以下が確実に切り捨てられること
  - **一貫した動作**: 四捨五入との差が出る値（.75）で切り捨てを明確に判別
- **テストの目的**: note.md「品質スコアが小数になる → 切り捨て」の仕様確認
  - **堅牢性の確認**: 端数処理仕様（切り捨て）がブレないこと。特性が発現しない構成でペナルティの影響を排除して純粋に平均切り捨てを検証
- 🟡 信頼性: note.md/要件定義書2.2の端数切り捨て仕様に基づく妥当な推測

### TC9: traitsが空/未設定の素材のみで発現なし 🟡

- **テスト名**: `test_traitsが空の素材のみでは発現なし`
  - **境界値の意味**: 特性タグが1つも存在しない（全素材 traits 空）という発現条件の下側境界
  - **境界値での動作保証**: 特性集計が空入力でも安全に動作し、発現0件を返すこと
- **入力値**: `[{"quality": 5, "traits": []}, {"quality": 2, "traits": []}]`
  - **境界値選択の根拠**: `pure_crystal`(S) + `plain_water`(C) 相当。特性タグ総数0の状態
  - **実際の使用場面**: 特性なし素材だけで調合するケース
- **期待される結果**: `result["traits"] == []`（空配列）、`result["quality"] == 3`（(5+2)/2=3）、`result["success"] == true`
  - **境界での正確性**: 特性集計ロジックが空 traits を安全に処理し、発現0件でペナルティ0
  - **一貫した動作**: 特性ありケース（TC2）と特性なしケース（TC9）で品質計算が一貫
- **テストの目的**: 特性が全く存在しない場合に発現・ペナルティが発生しないことの確認
  - **堅牢性の確認**: 空 traits 配列でクラッシュしないこと。TC1と合わせ「特性なし＝ペナルティなし」を担保
- 🟡 信頼性: REQ-106の発現条件からの裏面確認（妥当な推測）

### TC10: 投入枠フル4枠での調合成立 🟡

- **テスト名**: `test_投入枠フル4枠での調合成立`
  - **境界値の意味**: 投入枠の初期上限4枠（REQ-101）をフルに使った最大構成。配列長の上限境界
  - **境界値での動作保証**: 4要素の入力でも平均・特性集計が正しく動作すること
- **入力値**: `[{"quality": 5, "traits": []}, {"quality": 4, "traits": []}, {"quality": 3, "traits": []}, {"quality": 2, "traits": []}]`
  - **境界値選択の根拠**: RECIPE_DEFAULT_SLOT_COUNT = 4（REQ-101）の上限を使い切る構成。(5+4+3+2)/4 = 14/4 = 3.5 → 切り捨て 3
  - **実際の使用場面**: プレイヤーが全枠を埋めて調合する典型ケース
- **期待される結果**: `result["quality"] == 3`（3.5の切り捨て）、`result["success"] == true`、`result["traits"] == []`
  - **境界での正確性**: 4要素の平均と切り捨てが正しいこと
  - **一貫した動作**: 2要素（TC1）と4要素（TC10）で計算式が破綻しないこと
- **テストの目的**: 投入枠数の上限（4枠）での正常処理確認
  - **堅牢性の確認**: 最大枠数でクラッシュ・計算ずれが起きないこと
- 🟡 信頼性: REQ-101（投入枠4枠）に基づく妥当な推測

```gdscript
func test_特性の閾値発現_同一タグ2個で発現() -> void:

	# 【テスト内容】: contribution_holy を2個含む素材配列を resolve に渡す
	# 【期待される動作】: 完成品の traits に contribution_holy が含まれる
	# 🔵 信頼性: REQ-106, EDGE-101 に明記
```

### Given（準備フェーズ）

```gdscript
	# 【テストデータ準備】: 閾値ちょうど（2個）を再現するため同一タグの素材を2個用意する
	# 【初期条件設定】: quality は発現判定に影響しないよう任意値、traits を検証対象にする
	var materials: Array = [
		{"quality": 1, "traits": [&"contribution_holy"]},
		{"quality": 2, "traits": [&"contribution_holy"]},
	]
```

### When（実行フェーズ）

```gdscript
	# 【実際の処理実行】: 純粋関数 resolve を呼び出す
	# 【処理内容】: 基礎品質平均・特性発現判定・品質ペナルティを一括計算する
	var result: Dictionary = PrototypeAlchemyResolverScript.resolve(materials)
```

### Then（検証フェーズ）

```gdscript
	# 【結果検証】: 発現特性に contribution_holy が含まれるか検証する
	# 【期待値確認】: 同一タグ2個で発現するため has() が true
	# 【品質保証】: 閾値境界（2個）での発現保証がプロトタイプ仮説検証の前提となる
	assert_true(result["traits"].has(&"contribution_holy"), "同一特性2個ちょうどで発現するべき（EDGE-101）")
```
