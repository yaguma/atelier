## タスク概要

投入素材から「どの特性タグが完成品に発現するか」を判定する閾値発現ロジックを実装する。REQ-106（同一特性タグを持つ素材が2個以上の場合のみ発現、1個では不発）と、REQ-112（同一系統内での複数特性同時発現）を満たすほか、REQ-121〜124の段階的開示（ランクに応じて特性そのものを非表示・不発にする）を制御する。

本関数はGodotアーキテクトレビューCritical#1指摘への直接対応として設計された。旧設計案では関数内部で`GameState.current_rank`を参照する想定だったが、これは純粋関数の「入力のみに依存する」原則に違反するため、`reveal_level`（段階的開示レベル）を明示的な引数として受け取る設計に修正されている。呼び出し側（Imperative Shell、TASK-0019のGameState）が`current_rank.trait_reveal_level`を読み取って渡す。

貢献度系/報酬系をまたぐ排他制御（REQ-115）は本関数の責務ではなく、後続のTASK-0015（`resolve_category_conflict`）が担う。本関数は「閾値を満たしたか」の判定と、系統内の複数同時発現、および段階的開示によるフィルタリングまでを扱う。

## 実装詳細

### 1. TraitActivation.resolve_activated_traits 🔵

**信頼性**: 🔵 *architecture.md「Functional Core（logic/）」の関数シグネチャ例、dataflow.md「機能2」ステップ2より*

投入素材の`traits`配列を集計し、同一タグを持つ素材が2個以上ある特性のみを候補として抽出する（REQ-106）。同一系統（CONTRIBUTION同士、REWARD同士）内で複数の特性種類が閾値を満たす場合はすべて候補に含める（REQ-112。系統をまたぐ排他はTASK-0015の責務）。`reveal_level`によるフィルタリングをこの段階で適用し、非開示の特性は候補にすら含めない。

**実装ファイル**: `features/alchemy/logic/trait_activation.gd`

```gdscript
# 関数シグネチャ例
class_name TraitActivation
extends RefCounted

static func resolve_activated_traits(
    materials: Array[MaterialInstance],
    reveal_level: int,
    trait_definitions: Dictionary,  # StringName(trait id) -> TraitDefinition のマスターデータ参照
) -> Array[TraitDefinition]:
    pass
```

**信頼性補足**: 🟡 *`trait_definitions: Dictionary`引数はarchitecture.mdのシグネチャ例（`materials`, `reveal_level`の2引数のみ）には明記されていない追加パラメータ。`MaterialInstance.traits`はタグID（`StringName`）の配列であり、そのIDから`TraitDefinition.category`や解禁条件を判定するにはマスターデータの参照が不可欠なため、本タスクの実装判断として追加する。*

### 2. 閾値発現判定のアルゴリズム 🔵

**信頼性**: 🔵 *REQ-106, REQ-112より*

1. 投入素材全体から、`traits`配列に含まれる各タグIDの出現回数（＝そのタグを持つ素材の個数）を集計する
2. 出現回数が2以上のタグIDのみを候補とする（REQ-106「2個以上ある場合にのみ発現」、1個のみでは不発）
3. 各候補タグIDを`trait_definitions`辞書で`TraitDefinition`に解決する
4. `reveal_level`によるフィルタリング（後述）を適用する
5. 残った`TraitDefinition`をすべて返す（同一系統内の複数種類も含めて全て候補として残す。REQ-112「すべての該当特性を同時に完成品へ発現させなければならない」）

**実装ファイル**: `features/alchemy/logic/trait_activation.gd`

### 3. 段階的開示（reveal_level）フィルタリング 🔵

**信頼性**: 🔵 *REQ-121, REQ-122より。REQ-123は🟡（具体的な追加特性種類がTBDのため部分実装）*

- `reveal_level == 0`（Gランク、REQ-121）: 候補が何であってもフィルタ後は常に空配列を返す。品質のみで完成品を評価させるため
- `reveal_level >= 1`（Eランク以降、REQ-122）: 貢献度系・報酬系特性が解禁され、候補としてそのまま残る
- `reveal_level >= 2`（Dランク以降、REQ-123）: 追加の特性種類が解禁される想定だが、具体的にどの特性が追加されるかはTBDのため、本タスクでは`reveal_level >= 2`の場合に`reveal_level >= 1`と同じ扱い（追加フィルタなし）とする暫定実装とする。REQ-123の具体的な特性リストが確定した時点で追加のフィルタ条件を実装する必要がある（バランス調整フェーズ以降の追加タスクとして申し送り）

**実装ファイル**: `features/alchemy/logic/trait_activation.gd`

## 注意事項

- **Godotアーキテクトレビュー Critical#1の経緯**: 段階的開示（REQ-121〜124）はランク依存の情報だが、関数内で`GameState.current_rank`を直接参照すると「入力のみに依存する」という純粋関数の原則に違反する。このレビュー指摘を受け、`reveal_level`を明示的な引数として渡す設計に修正された。実装時にこの原則を絶対に破らないこと（`Engine.get_main_loop()`経由でのAutoload参照等の抜け道も禁止）。
- TASK-0011で申し送った`TraitDefinition.min_rank_to_reveal`（ランクID文字列）と本タスクの`reveal_level`（int）の対応関係は、本タスクでは簡略化してカテゴリ単位（CONTRIBUTION/REWARD全体をreveal_level>=1で解禁）のフィルタリングに留め、個別特性単位の解禁制御（REQ-123、Dランクでの追加）は暫定実装とする。REQ-123の具体的な特性リストが確定した際は、`min_rank_to_reveal`とint型`reveal_level`の変換方法を含めて再設計が必要になる可能性が高い（acceptance-criteria.md「未対応のまま残るWarning」にも同様の指摘あり）。
- TC-101-04, 05, 07（貢献度系/報酬系の系統排他）は本タスクの対象外。TASK-0015で実装する。本関数はあくまで「閾値を満たしたか」の判定のみを行い、系統間の優劣判定は行わない。
