## タスク概要

調合台画面 `features/alchemy/ui/alchemy_bench.tscn` + `alchemy_bench.gd`、および投入枠コンポーネント `material_slot.tscn` を実装する。ユーザストーリー2.1（限られた投入枠4枠に、在庫の素材から品質重視か特性重視かを選んで入れる）・2.2（貢献度向き/報酬向きを使い分ける）を実現するUIであり、TASK-0019で実装した `GameState.craft()` を呼び出し、`item_crafted(result: CraftResult)` signalの結果を表示する。

**重要な設計制約（architecture.md「Godotアーキテクトレビュー Warning#2対応」）**: 本UIは投入枠への素材配置操作と`item_crafted` signalの購読・結果表示のみを行う。品質計算・特性発現判定・貢献度/報酬算出などのビジネスロジックを一切持たない。これはTASK-0019の`GameState.craft()`実装で守られたFunctional Core/Imperative Shellの境界を、UI層でも継続して守るという意味を持つ。

## 実装詳細

### 1. alchemy_bench.gd 全体構成とImperative Shellとしての責務 🔵

**信頼性**: 🔵 *architecture.md「Godotアーキテクトレビュー Warning#2対応」『UIは投入枠の選択操作と、結果を受け取るsignal購読のみを行う』、dataflow.md「機能2: 調合」シーケンス図より*

`AlchemyBench`（`Control`継承）は、旧設計（UIが`QualityCalculator`→`TraitActivation`→`ValueCalculator`を個別に直接呼び出す）がWarning#2で否定されたことを踏まえ、`GameState.craft()`という単一のエントリポイントのみを呼び出す。BaseComponent相当の共通基盤はGodot版にまだ存在しないため、素直に`Control`継承のシーンスクリプトとして実装する。

```gdscript
# res://features/alchemy/ui/alchemy_bench.gd
extends Control
class_name AlchemyBench

@onready var slot_container: HBoxContainer = %SlotContainer
@onready var inventory_list: ItemList = %InventoryList
@onready var craft_button: Button = %CraftButton
@onready var result_panel: Control = %ResultPanel

var slots: Array[MaterialSlot] = []
var _placed_materials: Array[MaterialInstance] = []

func _ready() -> void:
    _build_slots(GameState.recipe_slot_count)
    _refresh_inventory()
    craft_button.pressed.connect(_on_craft_pressed)
    GameState.item_crafted.connect(_on_item_crafted)
    GameState.inventory_updated.connect(_refresh_inventory)
    _update_craft_button_state()

func _on_craft_pressed() -> void:
    # UIは選択済み素材の配列を渡すのみ。品質・特性・貢献度/報酬の計算は一切行わない
    GameState.craft(_placed_materials)

func _on_item_crafted(result: CraftResult) -> void:
    # CraftResultの値をそのまま表示に反映するのみ（再計算しない）
    result_panel.show_result(result)
```

**実装ファイル**: `atelier-godot/features/alchemy/ui/alchemy_bench.gd`, `atelier-godot/features/alchemy/ui/alchemy_bench.tscn`

### 2. material_slot.tscn（投入枠コンポーネント） 🟡

**信頼性**: 🟡 *architecture.md ディレクトリ構造「alchemy_bench.tscn（投入枠UI）＋material_slot.tscn」の記載から構成が存在することは🔵で裏付けられるが、具体的なコンポーネントの内部設計（クリックで配置/解除するトグル操作等）は設計文書に明記がないため妥当な推測*

投入枠1つを表すコンポーネント。空/埋まっているの2状態を持ち、埋まっている場合は配置された`MaterialInstance`の品質・特性タグ（表示可否はTASK-0037の段階的開示結線に委ねる。本タスクでは常時表示のプレースホルダとしてよい）を表示する。

```gdscript
# res://features/alchemy/ui/material_slot.gd
extends Control
class_name MaterialSlot

signal material_placed(material: MaterialInstance)
signal material_removed(material: MaterialInstance)

var placed_material: MaterialInstance = null

func is_empty() -> bool:
    return placed_material == null

func place(material: MaterialInstance) -> void:
    placed_material = material
    material_placed.emit(material)
    _update_display()

func clear() -> void:
    var removed := placed_material
    placed_material = null
    if removed != null:
        material_removed.emit(removed)
    _update_display()
```

**実装ファイル**: `atelier-godot/features/alchemy/ui/material_slot.gd`, `atelier-godot/features/alchemy/ui/material_slot.tscn`

func get_inventory() -> Array[MaterialInstance]:

### 4. 調合実行ボタンの活性化制御（EDGE-001） 🟡

**信頼性**: 🟡 *acceptance-criteria.md TC-101-E01「投入枠が空の場合、調合が成立せず、エラーまたは実行不可の状態になる」より。「実行不可の状態」をボタン非活性化として実装することは具体的なUI実装として妥当な推測*

投入枠が1つも埋まっていない状態では調合実行ボタンを非活性化し、そもそも`GameState.craft([])`が呼ばれないようにする。これはTASK-0019で`GameState.craft()`側にも実装済みの防御（`AlchemyResolver.craft()`が`null`を返した場合に状態変更・シグナル発行を行わない）とあわせた二重の安全策となる。

```gdscript
# res://features/alchemy/ui/alchemy_bench.gd （追記）
func _update_craft_button_state() -> void:
    craft_button.disabled = _placed_materials.is_empty()
```

**実装ファイル**: `atelier-godot/features/alchemy/ui/alchemy_bench.gd`

## UI/UX要件

### ローディング状態

- 調合は`NFR-101`（ローカル環境で完結、外部通信なし）に基づく同期処理のため、非同期ローディング表示（スピナー等）は不要。`GameState.craft()`呼び出しから`item_crafted`シグナル受信までは同一フレーム内で完結する前提とする

### エラー表示

- 投入枠が空の状態（EDGE-001）は、調合実行ボタンの非活性化のみで表現し、モーダルダイアログ等の明示的なエラーメッセージは表示しない（acceptance-criteria.md TC-101-E01の「実行不可の状態」という表現に沿う）
- 特性の発現・不発（REQ-115の排他制御等）は結果表示の一部として`CraftResult.activated_traits`・`rejected_category`をそのまま反映するのみとし、UI側で「なぜ不発になったか」の追加説明ロジックを持たない（Warning#2の境界を結果表示にも一貫させるため）

### アクセシビリティ

- 各投入枠・在庫アイテムは品質（D〜S）をアイコン+テキストで併記し、色のみに依存しない表現とする（design-guide.md「明瞭さ」原則）
- 特性タグの表示可否・具体的な見せ方（段階的開示に応じた表示制御）はTASK-0037のスコープであり、本タスクでは投入枠・結果表示に特性情報を表示するための土台（データバインディングの受け皿）のみを用意し、ランクに応じた表示ON/OFFの実装は行わない

## 注意事項

- **Imperative Shell/Functional Coreの境界を守ることが本タスクの最重要事項（TASK-0019と同じ境界）**: `alchemy_bench.gd`は「在庫参照→投入枠選択操作→`GameState.craft()`呼び出し→`item_crafted`シグナル受信→結果表示」のみを行い、品質計算・特性発現判定・貢献度/報酬算出のロジックを一切持たないこと。旧設計（UIが`QualityCalculator`等を個別に直接呼び出す）はWarning#2で明確に否定されており、将来の機能追加時にこの境界を破ってUI内に計算ロジックを書き足す誘惑が生じやすいため、レビュー時に特に注意すること（テストケース5・6がこの回帰を検知する）
- **`get_inventory()`メソッドの扱いに関する申し送り**: dataflow.mdのシーケンス図は`GameState.get_inventory()`という呼び出しを描いているが、data-model.mdの`GameState`構造定義には`inventory`フィールドのみが記載され、対応するアクセサメソッドの明記がない。本タスクでは薄いアクセサとして`get_inventory()`を追加する前提で実装するが、TASK-0019時点で`GameState`に同名メソッドが既に存在する場合はそちらを優先し、重複定義を避けること
- **段階的開示（reveal_level）との責務分離**: Gランクでの特性非表示（REQ-121, NFR-201）やEランク以降の解禁表示（REQ-122）は本タスクのスコープ外であり、TASK-0037が`alchemy_bench.gd`に`_update_trait_visibility()`等を追記する形で対応する。本タスクの時点では特性情報を常時表示するプレースホルダ実装で構わないが、TASK-0037が円滑に追記できるよう、特性表示部分を独立した関数・ノードとして分離しておくことが望ましい
- `current_recipe`（TASK-0019で`GameState`に追加された、現在有効なレシピ定義フィールド）を参照して投入枠数の表示を`recipe_slot_count`とどちらで決定するかは、data-model.mdに明記がなく実装時点でのGameStateの実際のフィールド構成に依存する。本タスクでは完了条件・テストケース3の通り`GameState.recipe_slot_count`を正とするが、実装時に`RecipeDefinition.slot_count`との整合（工房強化の反映がどちらに集約されるか）をTASK-0019・TASK-0034の実装状況と突き合わせて確認すること
