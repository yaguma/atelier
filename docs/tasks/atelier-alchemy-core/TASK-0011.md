## タスク概要

調合コアロジック（Phase 3）全体の入力データとなる2つの基礎データモデルを実装する。

- `TraitDefinition`（特性タグの静的定義。貢献度系/報酬系/補助系の3分類、段階的開示の解禁ランク情報を持つ）

この2クラスは以降の全ロジック関数（TASK-0013〜0018）の入力型として参照されるため、data-model.mdの型定義を過不足なく実装することが重要である。特に`TraitDefinition.category`の3分類（CONTRIBUTION/REWARD/SUPPORT）は、後続タスクの系統排他制御（REQ-115、TASK-0015）の判定基盤となる。

## 実装詳細

### 1. TraitDefinition（特性タグ定義） 🔵

**信頼性**: 🔵 *data-model.md「特性タグ（TraitDefinition）」より*

REQ-104（特性タグ0〜2個）、REQ-107（貢献度系/報酬系の分類）、REQ-108（補助系特性の分離）、REQ-121〜124（段階的開示の解禁ランク情報）を満たすResourceクラスとして実装する。

**実装ファイル**: `features/alchemy/data/trait_definition.gd`

```gdscript
# 型定義（data-model.mdより引用）
class_name TraitDefinition
extends Resource

enum Category {
    CONTRIBUTION,  # 貢献度系（例: 聖・浄・癒） REQ-107
    REWARD,        # 報酬系（例: 金・華・稀） REQ-107
    SUPPORT,       # 補助系（例: 触媒＝品質+1段） REQ-108
}

@export var id: StringName
@export var display_name: String
@export var category: Category
@export var min_rank_to_reveal: StringName
@export var bonus_multiplier: float = 1.0
```

### 2. MaterialInstance（素材インスタンス） 🔵

**信頼性**: 🔵 *data-model.md「素材インスタンス（MaterialInstance）」より*

REQ-103（品質値D〜S、スコア1〜5相当）、REQ-104（特性タグ0〜2個）を満たす実行時データとして実装する。マスターデータ（Resource）とは異なり、在庫ごとに個体差（品質・特性の組み合わせ）を持つためRefCountedとする。

**実装ファイル**: `features/alchemy/data/material_instance.gd`

```gdscript
# 型定義（data-model.mdより引用）
class_name MaterialInstance
extends RefCounted

enum Quality { D = 1, C = 2, B = 3, A = 4, S = 5 }  # REQ-103

var id: String
var seed_id: StringName
var quality: Quality
var traits: Array[StringName] = []  # REQ-104: TraitDefinition.idの配列、0〜2個

func _init(p_id: String = "", p_quality: Quality = Quality.D, p_traits: Array[StringName] = []) -> void:
    id = p_id
    quality = p_quality
    traits = p_traits
```

### 3. `min_rank_to_reveal`と`reveal_level`の対応関係（実装時の注意点） 🟡

**信頼性**: 🟡 *data-model.mdの2つの型定義間の整合性についての妥当な推測（設計文書に明記なし）*

`TraitDefinition.min_rank_to_reveal`はランクID（`StringName`、例: `"E"`, `"D"`）を保持する一方、`RankDefinition.trait_reveal_level`（TASK-0012以降で参照）は整数（`int`、0=特性なし, 1=貢献度/報酬解禁, 2=種類追加）である。architecture.mdの`resolve_activated_traits(materials, reveal_level: int)`はint型の`reveal_level`を引数に取るため、`min_rank_to_reveal`（ランクID文字列）と`reveal_level`（int）の対応関係をどこかで変換する必要がある。本タスクではデータモデルの型定義のみを扱い、変換ロジックの実装はTASK-0014（TraitActivation）のスコープとする。この対応関係が設計文書に明記されていない点は、TASK-0014着手時に設計判断が必要な既知の課題として申し送る。

## 注意事項

- REQ-111（品質ペナルティ改訂）の経緯: 旧設計では「1素材が複数特性タグを同時に持つ場合に品質・特性を無条件に両取りできる」支配戦略の抜け穴があった。これはREQ-104（0〜2個の特性タグ保持を許容するデータ構造）自体は変更せず、REQ-111/REQ-115（TASK-0015, 0016で実装）側でペナルティ・排他制御を強化することで対応した。本タスクのデータモデルは特性タグの複数保持を引き続き許容する設計のままでよい（支配戦略の防止はロジック層の責務）。
- REQ-124（未解禁特性素材の入手制限）はTraitDefinition自体に`min_rank_to_reveal`フィールドを持たせることで実現の土台とするが、実際の庭・ショップでの選択肢フィルタリングは本Phase 3（調合コアロジック）のスコープ外であり、別Feature（garden/workshop）のタスクで実装される。TC-121-E01（未解禁特性素材が選択肢に出ないことの確認）は、TraitActivation側の「二重の安全策」としてTASK-0014でも部分的に検証する（architecture.md「非機能要件の実現方法／ユーザビリティ」参照）。
- `min_rank_to_reveal`（ランクID文字列）と`reveal_level`（int、TASK-0014で使用）の対応関係は設計文書に明記がなく、TASK-0014着手時に変換方法を決定する必要がある（上記「実装詳細3」参照）。
