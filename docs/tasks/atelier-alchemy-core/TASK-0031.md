## 実装詳細

### 1. ランク進行順序の定義 🟡

**信頼性**: 🟡 *REQ-403「G→F→E→D→C→B→A→S 等」、コンセプト文書4章の体験カーブ表（G/F/E/D/C-B/A-S）より。正式なランク区分・数はTBD*

コンセプト文書の体験カーブ表から推測される8段階（G, F, E, D, C, B, A, S）を暫定の進行順序として定義する。正式な区分数・名称はTBDのため、balance-tuning-cycle等の後続フェーズで変更されうることをコメントで明記する。

```gdscript
# res://features/guild/logic/rank_progression.gd
class_name RankProgression
extends RefCounted

# 暫定のランク進行順序。正式な区分・数はTBD（REQ-403）
# コンセプト文書4章の体験カーブ表（G/F/E/D/C-B/A-S）から8段階と推測
const RANK_ORDER: Array[StringName] = [
	&"G", &"F", &"E", &"D", &"C", &"B", &"A", &"S",
]

static func get_next_rank_id(current_id: StringName) -> StringName:
	var idx: int = RANK_ORDER.find(current_id)
	if idx == -1 or idx >= RANK_ORDER.size() - 1:
		return &""  # 最上位ランク、または未知のランクID
	return RANK_ORDER[idx + 1]

static func is_final_rank(current_id: StringName) -> bool:
	return RANK_ORDER.find(current_id) == RANK_ORDER.size() - 1
```

**実装ファイル**: `features/guild/logic/rank_progression.gd`

### 2. trait_reveal_levelとの対応管理 🔵

**信頼性**: 🔵 *data-model.md「RankDefinition.trait_reveal_level」コメント、REQ-121〜124より*

段階的開示（REQ-121: Gランクは特性非発現、REQ-122: Eランク以降で貢献度系・報酬系解禁、REQ-123: Dランク以降で特性種類追加）とランク進行順序の対応を、マスターデータ作成時の参照テーブルとして定義する。Phase 6で想定される段階的開示のUI実装タスクは、ランクマスターデータの `trait_reveal_level` を直接参照するため、本テーブルは実装の手引きとしての位置づけとする。

```gdscript
# res://features/guild/logic/rank_progression.gd （続き）

# ランクIDごとのtrait_reveal_level対応（REQ-121〜123）。
# RankDefinitionマスターデータ作成時にこの値を設定する想定（Phase 6の段階的開示実装が参照）
const DEFAULT_TRAIT_REVEAL_LEVELS: Dictionary = {
	&"G": 0,  # REQ-121: 特性非発現
	&"F": 0,
	&"E": 1,  # REQ-122: 貢献度系・報酬系解禁
	&"D": 2,  # REQ-123: 特性種類追加（追加される具体的種類はTBD）
	&"C": 2,
	&"B": 2,
	&"A": 2,
	&"S": 2,
}
```

**実装ファイル**: `features/guild/logic/rank_progression.gd`

## 注意事項

- **ランクの正式な区分数・名称（REQ-403）はTBD**であり、本タスクではコンセプト文書の体験カーブ表から推測した暫定8段階（G/F/E/D/C/B/A/S）を用いる。balance-tuning-cycleスキル等の後続バランス調整フェーズで区分数が変更される可能性があるため、`RANK_ORDER` は他コードから直接ハードコードで参照させず、必ず `RankProgression` 経由でアクセスさせること
- `DEFAULT_TRAIT_REVEAL_LEVELS` はあくまで実装の手引き（デフォルト値のテーブル）であり、実際の `RankDefinition` マスターデータ（`.tres`）作成はPhase 6以降の別タスクで行う。本タスクではテーブルの定義と、進行順序との整合性検証のみを行う
- テストケース3（不正なランクID）は要件定義に明記のない防御的実装であるため、実装コストが見合わない場合は優先度を下げてよい
