## タスク概要

`autoload/game_state.gd` に、ランクHP枯渇による昇格試験移行（REQ-402、TASK-0029の後続処理）と、制限ターン超過による降格処理（REQ-205, REQ-206）の判定ロジックを実装する。EDGE-104「制限ターン（最終ターン）内にランクHPがちょうど0になった場合は、間に合ったものとみなし昇格試験へ移行させ、降格処理を行わない」という境界仕様を、判定順序の設計（ランクHP判定を納品直後に即時実行し、制限ターン判定はターン終了時に別途実行する）によって構造的に保証する。

## 実装詳細

### 1. ランクHP枯渇判定（即時・昇格試験移行） 🔵

**信頼性**: 🔵 *REQ-402「ランクHPが0になった場合、昇格試験へ移行しなければならない」より*

TASK-0029で実装した `_on_item_crafted` の末尾（`rank_hp` 減算直後）に判定を追加し、納品のたびに即座にHP枯渇をチェックする。この「即時判定」の設計がEDGE-104の境界仕様を構造的に保証する鍵となる（下記4.参照）。

```gdscript
# res://autoload/game_state.gd （既存GameStateへの追記）

func _on_item_crafted(result: CraftResult) -> void:
	# ...（TASK-0029の納品処理: rank_hp/gold更新、guild_delivered発行）...
	_check_rank_hp_depleted()

func _check_rank_hp_depleted() -> void:
	if rank_hp <= 0:
		rank_hp_depleted.emit()  # 昇格試験へ（workshop機能に遷移）
```

**実装ファイル**: `autoload/game_state.gd`

### 2. 制限ターン判定（ターン終了時・降格処理） 🟡

**信頼性**: 🟡 *REQ-205「各ランクに残りターン数の制限を設けなければならない」、REQ-206「制限ターン内にランクHPを0にできなかった場合、降格処理を行わなければならない」より。ターン進行を明示的にトリガーする`advance_turn()`のような関数の存在は他フェーズのターン管理実装に依存するため妥当な推測*

ターン終了時に呼び出される関数内で `remaining_turns` を減算し、その時点で `rank_hp > 0` のままであれば降格処理をトリガーする。`rank_hp > 0` のガード条件が、既に `rank_hp_depleted` が発行済み（昇格試験へ移行済み）のケースで `rank_failed` が二重に発行されることを防ぐ。

```gdscript
# res://autoload/game_state.gd （既存GameStateへの追記）

func advance_turn() -> void:
	remaining_turns -= 1
	if remaining_turns <= 0 and rank_hp > 0:
		rank_failed.emit()  # 降格処理（内容はTBD, REQ-206）
```

**実装ファイル**: `autoload/game_state.gd`

### 3. 降格処理の内容 🟡

**信頼性**: 🟡 *REQ-206「降格の具体的なペナルティ内容はTBD」より。未確定数値一覧（requirements.md）にも明記*

`rank_failed` signal発行後の具体的な降格処理内容（1段階降格か、再挑戦かなど）はTBDのため、本タスクでは`rank_failed` signalの発行条件（いつ降格判定が成立するか）のみを実装対象とし、降格後の状態遷移（ランクを1つ下げる等の具体的処理）は別タスクまたはbalance-tuning-cycleフェーズで確定させる。

**実装ファイル**: `autoload/game_state.gd`（signal発行部分のみ）

### 4. EDGE-104の境界仕様の保証設計 🔵

**信頼性**: 🔵 *EDGE-104「制限ターンちょうどでランクHPが0になった場合は間に合ったとみなし降格しない」より*

上記1・2の実装順序（HP判定は納品の都度即時実行、ターン判定はターン終了時に`rank_hp > 0`をガードとして実行）により、以下の流れでEDGE-104を満たす。

1. 最終ターンの納品で `rank_hp` が0以下になる
2. `_check_rank_hp_depleted()` が即座に `rank_hp_depleted` を発行する（昇格試験へ）
3. その後 `advance_turn()` が呼ばれても、`rank_hp > 0` のガード条件を満たさないため `rank_failed` は発行されない

これにより「間に合ったものとみなし、降格処理を行わない」という仕様を、判定順序の恣意的な調整ではなく構造的なガード条件で保証する。

**実装ファイル**: `autoload/game_state.gd`

### テストケース2: 制限ターンを使い切ってもランクHPが0にならない場合、降格する 🟡

**信頼性**: 🟡 *acceptance-criteria.md TC-402-E01, TC-201-E01より*

**When**: `advance_turn()` を呼ぶ
**Then**: `remaining_turns` が0になり、`rank_failed` signalが発行される

**テストファイル**: `tests/unit/features/guild/game_state_rank_progress_test.gd`

### テストケース3（境界値）: 制限ターンちょうどでランクHPが0になった場合は降格しない 🔵

**信頼性**: 🔵 *acceptance-criteria.md TC-201-B01、EDGE-104より*

**Given**: `remaining_turns = 1`（最終ターン）で、そのターン中の納品により `rank_hp` が0以下になった
**When**: 納品処理（`rank_hp_depleted`発行）の後に `advance_turn()` を呼ぶ
**Then**: `rank_failed` signalは発行されない（`rank_hp > 0` のガードにより降格判定がスキップされる）。`rank_hp_depleted` の発行のみが起きたことを確認する

**テストファイル**: `tests/unit/features/guild/game_state_rank_progress_test.gd`

## 注意事項

- **各ランクの制限ターン数（REQ-205）・降格時のペナルティ内容（REQ-206）はTBD**であり、balance-tuning-cycleスキル等の後続バランス調整フェーズで確定させる。本タスクでは`rank_failed` / `rank_hp_depleted` signalの**発行条件（いつ、どちらが発行されるか）**の正しさのみを実装・検証対象とし、降格の具体的な処理内容（ランクを1段階下げる、ペナルティを課す等）は含まない
