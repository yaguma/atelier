## タスク概要

発現した特性の数に応じて品質を減算する「品質ペナルティ」ロジックを実装する。REQ-111は2026-07-09のゲームデザインレビューを受けて確定した仕様で、コンセプト文書の「食い合い」（特性を宿すと品質を犠牲にする）という意図を、投入枠の配分ではなく品質スコアへの直接ペナルティとして数式化したものである。

旧版（枠数ベースの食い合い）は「1素材が複数特性タグを同時に持つ場合に品質・特性・貢献度・報酬を無条件に両取りできる」支配戦略の抜け穴を持っていたため、レビューにより本方式へ差し替えられた経緯がある。本タスクはTASK-0013（基礎品質）とTASK-0015（系統排他制御後の最終発現特性）の出力を受け取り、最終品質を算出する。

## 実装詳細

### 1. QualityCalculator.apply_trait_penalty 🔵

**信頼性**: 🔵 *REQ-111、architecture.mdの関数シグネチャ例より*

TASK-0013の`calculate_base_quality`が返した基礎品質（`float`）と、TASK-0015の`resolve_category_conflict`が返した最終発現特性（系統排他適用後）を受け取り、最終品質を算出する。

**実装ファイル**: `features/alchemy/logic/quality_calculator.gd`（TASK-0013と同一ファイル）

```gdscript
# 関数シグネチャ例
static func apply_trait_penalty(
    base_quality: float,
    activated_traits: Array[TraitDefinition],
) -> MaterialInstance.Quality:
    pass
```

**信頼性補足**: 🟡 *戻り値型を`MaterialInstance.Quality`（int enum、1〜5）とする判断はTASK-0013で申し送った「floatからQuality enumへの変換ポイント」を本関数に置くという実装判断。CraftResult.final_quality（data-model.md）が`MaterialInstance.Quality`型であるため、CraftResultへ格納する直前の本関数でfloat→int変換を行うのが妥当と判断した。float→int変換の丸め方式（四捨五入/切り捨て等）は設計文書に明記がないため、`round()`（四捨五入）を暫定採用し、コードコメントで明示する。数値バランス上の妥当性は`balance-tuning-cycle`等の後続フェーズで再検証すること。*

### 2. ペナルティ算出アルゴリズム 🔵

**信頼性**: 🔵 *REQ-111, REQ-112, REQ-108より*

1. `activated_traits`のうち`category != SUPPORT`の件数を数える（`penalty_count`）
2. `quality_after_penalty = base_quality - penalty_count`（REQ-111「発現特性1個につき...1段階減算」、REQ-112「加算的に積み重なる」）
3. `activated_traits`のうち`category == SUPPORT`の件数を数える（`support_bonus_count`）
4. `quality_after_penalty += support_bonus_count`（REQ-111「補助系特性の効果はこの減算後に加算する」、REQ-108「触媒＝品質+1段」）
5. 下限クランプ: `quality_after_penalty = max(quality_after_penalty, 1.0)`（REQ-111「最終品質はD＝スコア1を下回ってはならない」）
6. 上限クランプ: `quality_after_penalty = min(quality_after_penalty, 5.0)` 🟡（要件定義に明記はないが、`MaterialInstance.Quality`の値域が1〜5であるための防御的実装）
7. `round()`で最も近い整数に丸め、`MaterialInstance.Quality`にキャストして返す

**実装ファイル**: `features/alchemy/logic/quality_calculator.gd`

## 注意事項

- **REQ-111改訂の経緯（最重要）**: 本ロジックは支配戦略の抜け穴を塞ぐために2026-07-09に確定した仕様である。実装時に「ペナルティを枠の配分で表現する」旧版のロジックに戻さないこと。品質スコアへの直接減算という数式レベルでの実装を維持する。
- 補助系（触媒）が複数同時に発現した場合の扱い（+1段が加算的に積み重なるか、上限があるか）はREQ-108本文に明記がなく、本タスクでは「補助系の件数分だけ加算する」という単純な加算モデルを採用した（🟡）。触媒の複数投入がバランス上どう扱われるべきかは、バランス調整フェーズで再検討が必要な可能性がある。
- float→int（`MaterialInstance.Quality`）変換の丸め方式（`round()`採用）はTASK-0013から続く設計文書間の不整合（int想定のシグネチャ例 vs 非整数を許容する期待結果）に対する暫定対応である。実装時にTASK-0013のコメントと合わせて一貫した変換ポイントであることを確認すること。
