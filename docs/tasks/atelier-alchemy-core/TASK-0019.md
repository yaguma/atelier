## タスク概要

`GameState` Autoload（Imperative Shell）に、TASK-0018で実装した`AlchemyResolver.craft()`（Functional Core）を呼び出す`craft()`メソッドを実装する。data-model.md「GameState Autoloadの状態構造」に明記された通り、`GameState`は自身が保持する`current_rank.trait_reveal_level`と`today_request`を引数として`AlchemyResolver.craft()`に渡し、Autoload参照を純粋関数側に一切漏らさない。戻り値の`CraftResult`を用いて在庫・ランクHP・ゴールドを更新し、`item_crafted`シグナルを発行する。

本タスクは調合コアロジック（Phase 3）における、純粋関数（Functional Core）と副作用を持つ層（Imperative Shell）の境界を実際に接続する最初のタスクである。この境界を正しく守ること（`GameState`側が状態読み取り・引数渡し・状態更新・シグナル発行のみを担当し、計算ロジック自体は一切持たないこと）が本タスクで最も重要な設計上の要点である。

## 実装詳細

### 1. GameState.craft() 🔵

**信頼性**: 🔵 *data-model.md「GameState Autoloadの状態構造」の`craft()`定義より*

**実装ファイル**: `autoload/game_state.gd`

```gdscript
# 型定義（data-model.mdより引用・拡張）
extends Node

signal item_crafted(result: CraftResult)
# 他のシグナル・状態変数はdata-model.md「GameState Autoloadの状態構造」を参照

var current_rank: RankDefinition
var rank_hp: int
var gold: int = 0
var inventory: Array[MaterialInstance] = []
var today_request: DailyRequest

func craft(materials: Array[MaterialInstance]) -> void:
    # GameState（Imperative Shell）がcurrent_rank.trait_reveal_levelとtoday_requestを引数として
    # AlchemyResolver.craft()（Functional Core, static func）に渡す。Autoload参照を純粋関数側に漏らさない。
    var result: CraftResult = AlchemyResolver.craft(
        materials,
        current_rank.trait_reveal_level,
        today_request,
        current_recipe,       # TASK-0018で追加された引数。現在有効なレシピ定義
        trait_definitions,    # TASK-0014で追加された引数。特性マスターデータ辞書
    )
    if result == null:
        return  # EDGE-001: 投入枠が空等、調合が成立しない場合は何もしない

    _consume_materials(materials)
    rank_hp -= int(round(result.contribution))
    gold += int(round(result.reward))
    item_crafted.emit(result)
```

**信頼性補足**: 🟡 *`current_recipe`・`trait_definitions`のGameStateフィールドは、TASK-0018で拡張された`AlchemyResolver.craft()`のシグネチャに対応するために本タスクで追加が必要になった、data-model.md未記載のフィールド。マスターデータ（`trait_definitions`）をどのタイミングで読み込みGameStateに保持するかは、本タスクのスコープでは「起動時に一括読み込み済み」という前提を置く（architecture.md「非機能要件の実現方法／パフォーマンス」の「マスターデータはロード時に一括読み込みし、実行中の動的ファイルI/Oを避ける」方針に整合）。*

### 2. `_consume_materials`ヘルパーの実装 🟡

**信頼性**: 🟡 *dataflow.md「機能2」の`consume_materials(投入素材) + add_completed_item(完成品)`より*

投入に使用した`materials`を`inventory`配列から取り除く。GDScriptの`Array`比較はデフォルトで値比較のため、`MaterialInstance`が`id`で一意に識別されることを利用し、`id`一致で除去する。

**実装ファイル**: `autoload/game_state.gd`

```gdscript
func _consume_materials(materials: Array[MaterialInstance]) -> void:
    for material in materials:
        var index := inventory.find(material)
        if index != -1:
            inventory.remove_at(index)
    inventory_updated.emit()
```

## 注意事項

- **Imperative Shell/Functional Coreの境界を守ることが本タスクの最重要事項**: `GameState.craft()`は「状態の読み取り→純粋関数への引数渡し→戻り値を用いた状態更新→シグナル発行」のみを行い、品質計算・特性発現判定・系統排他制御・貢献度/報酬算出のロジックを一切持たないこと。将来の機能追加時にこの境界を破って`GameState`内に計算ロジックを書き足す誘惑が生じやすいため、レビュー時に特に注意すること（テストケース5がこの回帰を検知する）。
- **dataflow.mdとの不整合に関する申し送り**: dataflow.md「機能2: 調合」のシーケンス図では、GameStateは`consume_materials(投入素材) + add_completed_item(完成品)`のみを行い、`rank_hp`/`gold`の更新は別の「機能3: ギルド納品」シーケンス（`item_crafted`シグナルを起点に`DeliveryCalculator.check_daily_request_match()`を経由）で行われる設計になっている。一方、data-model.mdの`craft()`定義は「戻り値のCraftResultを用いてinventory/rank_hp/goldを更新し、item_craftedをemitする」と明記しており、`craft()`単体でrank_hp/goldまで更新する設計になっている。本タスクはプロンプトで与えられたタスク定義（data-model.mdの記述を直接実装対象とする）に従い後者の設計を採用したが、これは前者（dataflow.mdの機能3分離設計）と矛盾する。TASK-0017で申し送った「指定合致ボーナスの二重適用疑義」とも関連するため、**Phase 4（guild機能）着手前に、rank_hp/gold更新の責務をcraft()単体で完結させるのか、guild機能の別ステップに委ねるのかを設計レベルで確定させる必要がある**。
- `current_recipe`・`trait_definitions`フィールドの読み込みタイミング・保持方法はdata-model.mdに明記がないため、本タスクでは「起動時に一括読み込み済み」を前提とする。実際のロード処理（`.tres`ファイルからの読み込み）は別タスク（マスターデータ管理、Phase 1/2のスコープ）に依存する可能性があり、依存関係の再確認が必要な場合はタスク分割の見直しを検討すること。
