## タスク概要

工房強化（金の使い道）機能の土台となる `UpgradeDefinition` リソースクラスを実装する。恒久投資（PERMANENT）と消耗投資（CONSUMABLE）を `Kind` enumで明確に区分し、後続タスク（TASK-0034の恒久投資ロジック、TASK-0035の消耗投資ロジック）がこの区分を前提に購入可否を制御できるようにする。本タスクはPhase 6の起点であり、data-model.mdで既に確定している型定義をそのままGodotリソースクラスとして実装する。

- **後続タスク**: [TASK-0034: 恒久投資ロジック・PermanentUpgradeScreen実装](TASK-0034.md), [TASK-0035: 消耗投資ロジック・ConsumableShopPanel実装](TASK-0035.md)

## 実装詳細

### 1. UpgradeDefinitionリソースクラス 🔵

**信頼性**: 🔵 *data-model.md「工房強化定義（UpgradeDefinition）」より*

data-model.mdに定義された型をそのまま実装する。

```gdscript
# res://features/workshop/data/upgrade_definition.gd
class_name UpgradeDefinition
extends Resource

enum Kind {
    PERMANENT,   # 恒久投資: ランク間強化画面でのみ購入可 REQ-301, REQ-304
    CONSUMABLE,  # 消耗投資: ターン中いつでも購入可 REQ-302, REQ-305
}

@export var id: StringName            # 例: "slot_plus_one", "garden_expand", "recipe_unlock", "catalyst", "seed_pick"
@export var kind: Kind
@export var price: int = 0            # REQ-306の価格序列より。具体値はTBD
@export var display_name: String

func is_permanent() -> bool:
    return kind == Kind.PERMANENT

func is_consumable() -> bool:
    return kind == Kind.CONSUMABLE
```

**実装ファイル**: `atelier-godot/features/workshop/data/upgrade_definition.gd`

### 2. `is_permanent()` / `is_consumable()` ヘルパーメソッド 🟡

**信頼性**: 🟡 *data-model.mdにはenum定義のみ明記され、判定メソッドの明記はないが、TASK-0034/0035が「恒久投資のみ」「消耗投資のみ」を絞り込む処理を持つことから妥当な推測（テスト可能な最小ロジックとして追加）*

`kind` を直接比較する代わりに意図が明確なメソッドを提供する。後続タスクの `upgrade_cost_table.gd` や購入可否チェックロジックがこのメソッドに依存する。

**実装ファイル**: `atelier-godot/features/workshop/data/upgrade_definition.gd`（同一ファイル内）

### 3. 5種類の工房強化項目のテストデータ 🔵

**信頼性**: 🔵 *REQ-301「投入枠+1・庭拡張・レシピ解禁」、REQ-302「触媒の常備・購入、種の指名買い」、REQ-306の価格序列（投入枠+1≫庭拡張≒レシピ解禁＞触媒＞種の指名買い）より*

テスト内で以下5種のインスタンスを生成し、`kind` の区分が意図通りであることを検証する。

| id | kind | 用途 |
|---|---|---|
| `slot_plus_one` | PERMANENT | 投入枠+1（REQ-102, REQ-301） |
| `garden_expand` | PERMANENT | 庭拡張（REQ-301） |
| `recipe_unlock` | PERMANENT | レシピ解禁（REQ-301） |
| `catalyst` | CONSUMABLE | 触媒の常備・購入（REQ-108, REQ-302） |
| `seed_pick` | CONSUMABLE | 種の指名買い（REQ-302） |

**実装ファイル**: `atelier-godot/tests/unit/features/workshop/upgrade_definition_test.gd`

## 単体テスト要件（TDDタスク）

### テストケース1: PERMANENTのUpgradeDefinitionを生成する 🔵

**信頼性**: 🔵 *REQ-301, data-model.md UpgradeDefinition.Kindより*

**Given**: `id = "slot_plus_one"`, `kind = Kind.PERMANENT` を指定
**When**: `UpgradeDefinition` インスタンスを生成する
**Then**: `is_permanent()` が `true`、`is_consumable()` が `false` を返す

### テストケース2: CONSUMABLEのUpgradeDefinitionを生成する 🔵

**信頼性**: 🔵 *REQ-302, data-model.md UpgradeDefinition.Kindより*

**Given**: `id = "catalyst"`, `kind = Kind.CONSUMABLE` を指定
**When**: `UpgradeDefinition` インスタンスを生成する
**Then**: `is_consumable()` が `true`、`is_permanent()` が `false` を返す

### テストケース3: priceのデフォルト値 🟡

**信頼性**: 🟡 *data-model.md `price: int = 0`（TBD）より*

**Given**: `price` を明示的に指定せずインスタンスを生成する
**When**: `price` プロパティを参照する
**Then**: デフォルト値 `0` が返る（具体的な価格はバランス調整で確定、REQ-306参照）

### テストケース4: 5種類の工房強化項目がKindで正しく分類される 🔵

**信頼性**: 🔵 *REQ-301, REQ-302の項目一覧、REQ-306の価格序列前提より*

**Given**: 上記テストデータ表の5種類の `UpgradeDefinition` インスタンス一覧
**When**: `kind` でフィルタリングする
**Then**: `slot_plus_one` / `garden_expand` / `recipe_unlock` がPERMANENT側に、`catalyst` / `seed_pick` がCONSUMABLE側に分類される

## 注意事項

- 本タスクはデータモデルの実装に限定し、価格の具体的な数値決定（REQ-306の`TBD`）や購入可否チェックロジック自体はTASK-0034（恒久投資）・TASK-0035（消耗投資）で行う

- ターン延長に相当する `kind` や `id`（例: `extend_turn` 等）は本タスクのテストデータに一切含めないこと。REQ-303（金でターンを延長できない、設計上の核心制約）はTASK-0036で明示的に検証するが、本タスクの時点から延長系項目を作らないことが前提となる
