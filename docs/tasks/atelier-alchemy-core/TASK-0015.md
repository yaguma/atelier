## タスク概要

貢献度系特性と報酬系特性が同時に発現条件（REQ-106）を満たした場合の排他制御を実装する。これは2026-07-09のゲームデザインレビューで指摘された **Critical 2: 貢献度/報酬の二分ジレンマ破壊** への直接対応として新設された要件（REQ-115）であり、本Phase 3の中でも最重要度の高いロジックの1つである。

旧設計では「1品で貢献度系・報酬系の両方を無条件に発現させられる」支配戦略（最適解が自明になり、選択の意味がなくなる状態）が存在した。REQ-115はこれを防ぐため、投入枠内で条件を満たしている枚数（同一タグの重複投入数の合計）を系統ごとに比較し、より多い系統のみを発現させる。同数の場合はどちらの系統も発現させない。これにより、コンセプト文書が意図する「独自要素2: 特性の二分による真のジレンマ」を数式レベルで保証する。

TC-101-07は「1素材が貢献度系・報酬系の両方のタグを同時に持つ場合でも、無条件な両取りができない」ことを検証する最重要ケースであり、REQ-104（素材が特性タグを0〜2個持てるデータ構造）とREQ-115（系統排他）が組み合わさって初めて支配戦略を防げることを確認する。

## 実装詳細

### 1. TraitActivation.resolve_category_conflict 🔵

**信頼性**: 🔵 *dataflow.md「機能2」ステップ3「resolve_category_conflict(発現特性) — REQ-115」より*

TASK-0014の`resolve_activated_traits`が返した発現候補（`activated_traits`）を受け取り、REQ-115の系統排他制御を適用した最終結果を返す。CraftResultの`rejected_category`（TASK-0012で型定義のみ先行実装済み、無効値表現は本タスクで確定）を構成するための情報も合わせて返す。

**実装ファイル**: `features/alchemy/logic/trait_activation.gd`（TASK-0014と同一ファイル）

```gdscript
# 関数シグネチャ例
static func resolve_category_conflict(
    materials: Array[MaterialInstance],
    activated_traits: Array[TraitDefinition],
) -> Dictionary:
    # 戻り値: {
    #   "activated_traits": Array[TraitDefinition],  # 排他制御後の最終発現特性
    #   "rejected_category": TraitDefinition.Category,  # 不発とされた系統（同数不発の場合は無効値、後述）
    #   "has_rejected_category": bool,  # rejected_categoryが有効な値かどうか
    # }
    pass
```

**信頼性補足**: 🟡 *`materials`引数の追加はTASK-0014と同様、architecture.mdのシグネチャ例に明記のない実装判断。系統ごとの「条件を満たしている枚数（同一タグの重複投入数の合計）」（REQ-115）を算出するには、発現特性のリストだけでなく元の投入素材を参照して各タグの出現数を再集計する必要があるため追加する。*

### 2. 系統別枚数の集計と比較アルゴリズム 🔵

**信頼性**: 🔵 *REQ-115「投入枠内で条件を満たしている枚数（同一タグの重複投入数の合計）がより多い系統のみを発現させ」より*

1. `activated_traits`を`category`でグループ化する（CONTRIBUTION群 / REWARD群 / SUPPORT群）
2. CONTRIBUTION群・REWARD群それぞれについて、各特性タグを持つ`materials`の個数を合計する（例: 「聖」2個+「浄」2個が両方ともCONTRIBUTION群に属する場合、CONTRIBUTION群の合計枚数は4）
3. CONTRIBUTION合計とREWARD合計を比較する
   - 一方が多い場合: 多い方の系統の特性のみ`activated_traits`に残し、少ない方の系統の特性を全て除外する。除外された系統を`rejected_category`として返す（`has_rejected_category = true`）
   - 同数の場合（両方とも0件でない場合）: 両方の系統の特性を`activated_traits`から除外する。この場合「不発とされた系統」は単一の値で表現できない（両方が不発のため）ため、`has_rejected_category = false`とし、`rejected_category`は無効値のまま扱う（詳細は「注意事項」参照）
   - 一方が0件（そもそも候補が存在しない）の場合: 排他制御の対象外として、存在する方の系統をそのまま残す
4. SUPPORT群は上記の比較対象に含めず、常に`activated_traits`に残す（REQ-115最終文「補助系特性はこの排他制御の対象外とする」）

**実装ファイル**: `features/alchemy/logic/trait_activation.gd`

## 単体テスト要件

### テストケース1: 貢献度系・報酬系が同数（2枚 vs 2枚）で両方とも不発になる（TC-101-04） 🔵

**信頼性**: 🔵 **Critical** *acceptance-criteria.md TC-101-04より。2026-07-09のゲームデザインレビューCritical指摘への直接対応*

**Given**: 特性「聖」（貢献度系）2個 + 特性「金」（報酬系）2個から成る発現候補

**テストファイル**: `tests/unit/features/alchemy/trait_activation_test.gd`

**信頼性**: 🔵 *acceptance-criteria.md TC-101-05より*

**Given**: 投入枠5枠（工房強化後）に特性「聖」（貢献度系）3個 + 特性「金」（報酬系）2個から成る発現候補
**When**: `resolve_category_conflict(materials, activated_traits)`を呼び出す
**Then**: 戻り値の`activated_traits`に「聖」のみが含まれる（`size() == 1`）。`rejected_category == TraitDefinition.Category.REWARD`、`has_rejected_category == true`

**テストファイル**: `tests/unit/features/alchemy/trait_activation_test.gd`

### テストケース3: 1素材が2タグを同時保持しても無条件両取りできない（TC-101-07） 🔵

**信頼性**: 🔵 **Critical** *acceptance-criteria.md TC-101-07より。2026-07-09のゲームデザインレビュー「Critical 1: 食い合いが支配戦略を許す」への直接対応。本フェーズで最も重要なテストケースの1つ*

**Given**: 「聖」（貢献度系）「金」（報酬系）の両タグを持つ素材2個 + 高品質無特性素材2個。「聖」「金」ともに閾値2個を満たす発現候補
**When**: `resolve_category_conflict(materials, activated_traits)`を呼び出す
**Then**: CONTRIBUTION合計2件・REWARD合計2件で同数となり、TC-101-04と同じ同数不発ルールが適用される。戻り値の`activated_traits`が空配列になる。無条件に高品質かつ両特性を同時に得る組み合わせが成立しないことを確認する

**テストファイル**: `tests/unit/features/alchemy/trait_activation_test.gd`

## 注意事項

- **ゲームデザインレビューの経緯（最重要）**: REQ-115は2026-07-09に新設された要件で、「貢献度系・報酬系を1品で無条件に両取りできる」支配戦略を防ぐことが目的である。TC-101-04・TC-101-07はこの支配戦略防止を直接検証する最重要ケースであり、実装時にこの2ケースを軽視しないこと。もし実装が誤ってこれらのケースで「両方発現」を許してしまうと、ゲームデザインレビューで指摘されたCritical不具合が再発することになる。
- **CraftResult.rejected_categoryの無効値表現（TASK-0012からの申し送り事項の確定）**: 同数不発の場合、「不発とされた系統」は貢献度系・報酬系の両方であり単一のenum値では表現できない。本タスクでは`has_rejected_category: bool`フラグを追加した`Dictionary`を戻り値とすることでこれを解決する。`AlchemyResolver.craft()`（TASK-0018）が`CraftResult`にこの結果を格納する際は、`has_rejected_category == false`の場合`CraftResult.rejected_category`を意味のない値（例: デフォルトの`Category.CONTRIBUTION`）のまま残し、UI側（TASK-0020）は`has_rejected_category`相当のフラグ（`CraftResult`に追加が必要な場合はTASK-0012の型定義を拡張する）を必ず確認してから`rejected_category`を参照すること。この点はdata-model.mdのCraftResult定義には明記されていないギャップであり、TASK-0018実装時に`CraftResult`へのフィールド追加（例: `has_rejected_category: bool`）が必要になる可能性が高い。
- REQ-112（同一系統内の複数特性同時発現、TASK-0014）とREQ-115（系統間排他、本タスク）は適用順序が異なる処理であることに注意する。同一系統内の複数発現はTASK-0014で確定済みの状態を前提とし、本タスクはその「確定済みの系統別集合」同士を比較するのみで、系統内の個別特性を再評価しない。
