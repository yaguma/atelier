## タスク概要

恒久投資（投入枠+1・庭拡張・レシピ解禁）の購入ロジックと、それを提示する `PermanentUpgradeScreen` を実装する。恒久投資は「ランク間の工房強化画面でのみ購入可能」（REQ-304）という制約を持ち、購入した効果はランクをまたいで永続する（REQ-301）。価格は `投入枠+1 ≫ 庭拡張 ≒ レシピ解禁` の序列（REQ-306）に従う。dataflow.md「機能4: 工房強化」シーケンス図の `purchase_permanent_upgrade(upgrade_id)` フローをGameState Autoloadに実装し、UIはそれを呼び出すだけの薄い層とする。

### 2. GameState.purchase_permanent_upgrade() 🔵

**信頼性**: 🔵 *dataflow.md「機能4: 工房強化」シーケンス図の `purchase_permanent_upgrade(upgrade_id)` フローより*

dataflow.mdのシーケンス図通り、Imperative Shell（`GameState` Autoload）にゴールド減算・`permanent_upgrades`配列への追加を集約する。UI側はビジネスロジックを持たない。

```gdscript
# res://autoload/game_state.gd （追記）
func purchase_permanent_upgrade(upgrade_id: StringName) -> bool:
    if not is_permanent_upgrade_screen_active:  # REQ-304: ランク間強化画面でのみ許可
        return false
    var def := _find_permanent_upgrade_definition(upgrade_id)
    if def == null or gold < def.price:
        return false
    gold -= def.price
    permanent_upgrades.append(upgrade_id)
    if upgrade_id == &"slot_plus_one":
        recipe_slot_count += 1  # REQ-102
    upgrades_updated.emit()
    return true
```

**実装ファイル**: `atelier-godot/autoload/game_state.gd`

### 3. permanent_upgrade_screen.tscn（ランク間強化画面UI） 🔵

**信頼性**: 🔵 *REQ-304「恒久投資の購入をランク間の工房強化画面でのみ許可」、ユーザストーリー4.1「工房強化画面が開き、恒久投資の選択肢が提示される」より*

昇格試験クリア後にのみ表示される専用画面。恒久投資3項目をカードまたはリストで並べ、所持ゴールドと価格を表示し、購入可否（ゴールド不足時は非活性化）を視覚的に示す。

**実装ファイル**: `atelier-godot/features/workshop/ui/permanent_upgrade_screen.tscn`, `permanent_upgrade_screen.gd`

### 4. ランク間強化画面のアクティブ状態管理 🟡

**信頼性**: 🟡 *REQ-304からの妥当な推測。「ランク間」という文脈をシステムがどう判定するかはarchitecture.md/dataflow.mdに明記がないため、フラグ方式で実装*

`GameState` に `is_permanent_upgrade_screen_active: bool` を持たせ、昇格試験クリア時（`rank_hp_depleted` signal後）に `true`、次ランクの通常ターンが開始した時点で `false` に戻す。これによりTASK-0036・TC-301-E02（ターン中の恒久投資購入拒否）の判定基盤とする。

**実装ファイル**: `atelier-godot/autoload/game_state.gd`

## 単体テスト要件（TDDタスク）

### テストケース1: ランク間強化画面で投入枠+1を購入する（TC-301-01） 🔵

**信頼性**: 🔵 *acceptance-criteria.md TC-301-01より*

**Given**: 昇格試験クリア後（`is_permanent_upgrade_screen_active = true`）、所持ゴールドが`slot_plus_one`の価格以上
**When**: `GameState.purchase_permanent_upgrade(&"slot_plus_one")` を呼ぶ
**Then**: 購入が成立し、`recipe_slot_count` が4から5になり、次ランク以降も5枠のまま維持される

### テストケース2: 恒久投資はランクをまたいで永続する 🔵

**信頼性**: 🔵 *REQ-301「これらはランクをまたいで効果が持続しなければならない」より*

**Given**: `slot_plus_one` を購入済みの状態でランクが進行する
**When**: 次のランクの調合を開始する
**Then**: `recipe_slot_count` は5枠のまま（リセットされない）

### テストケース3: 価格序列の検証 🟡

**信頼性**: 🟡 *REQ-306の序列は🔵だが具体値はTBDのため🟡*

**Given**: `UpgradeCostTable.PERMANENT_PRICES` の3項目
**When**: 価格を比較する
**Then**: `slot_plus_one` の価格が `garden_expand` および `recipe_unlock` の価格を大きく上回り（≫）、`garden_expand` と `recipe_unlock` はほぼ同額（≒）である

### テストケース4: ターン中に恒久投資の購入を試みると拒否される（TC-301-E02） 🟡

**信頼性**: 🟡 *acceptance-criteria.md TC-301-E02より*

**Given**: 通常ターン中（`is_permanent_upgrade_screen_active = false`）、所持ゴールドが十分
**When**: `GameState.purchase_permanent_upgrade(&"slot_plus_one")` を呼ぶ
**Then**: 購入が拒否され（戻り値`false`）、`gold`・`permanent_upgrades`・`recipe_slot_count`のいずれも変化しない

### テストケース5: ゴールド不足時の購入拒否 🟡

**信頼性**: 🟡 *REQ-301, REQ-304からの妥当な拡張（一般的な購入ロジックの前提条件）*

**Given**: ランク間強化画面が有効、所持ゴールドが価格未満
**When**: `GameState.purchase_permanent_upgrade(upgrade_id)` を呼ぶ
**Then**: 購入が拒否され、`gold`は変化しない

## UI/UX要件

### ローディング状態

- 恒久投資はローカル完結の同期処理（NFR-101, dataflow.md「同期処理のみ」）のため、非同期ローディング表示は不要

### エラー表示

- ゴールド不足の項目は購入ボタンを非活性化し、価格テキストを警告色で示す（design-guide.mdの色トークンを使用し、独自色のハードコードは禁止）
- ターン中に誤って本画面を開こうとする導線自体をmain.tscn側（TASK-0038）で作らないことを基本方針とし、本画面はランク間強化画面としてのみ遷移可能にする

### アクセシビリティ

- 各恒久投資項目のカードには効果内容（投入枠+1／庭拡張／レシピ解禁）をアイコン+テキストで併記する（design-guide.md「明瞭さ」原則）
- 購入確定前に効果内容の確認ダイアログ等は必須としない（本要件定義のスコープ外、UXの作り込みは簡潔に留める）

## 注意事項

- 本タスクで実装する恒久投資項目（投入枠+1・庭拡張・レシピ解禁）に「ターン延長」に相当する項目を一切含めないこと。REQ-303（金でターンを延長できない、意図的な除外という設計上の核心制約）はTASK-0036で横断的に検証するが、本タスクの実装時点から違反しないことが前提
- 価格の具体値（`UpgradeCostTable.PERMANENT_PRICES`）はTBDの仮値であり、`balance-tuning-cycle`スキル等の後続バランス調整で正式に確定させる
- 「ランク間強化画面がいつアクティブになるか」の判定はTASK-0031（他フェーズ）のランク進行管理との結線が前提のため、本タスク単体では `is_permanent_upgrade_screen_active` フラグの手動セットでテストを完結させてよい
