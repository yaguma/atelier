# TASK-0010 プロトタイプ検証記録（プレイテスト手順 + AI自己検証結果）

## 0. 本記録の位置づけ（重要な注意事項）

> **本記録はAIエージェントによる自己検証（擬似プレイテスト）であり、TC-501-H01が本来意図する「第三者（人間）による反応観察」ではない。**
>
> - 「素材選択時に一瞬迷うか」という仮説は、人間の認知・判断プロセスに関する仮説である。AIエージェントには「迷い」（考える時間の発生、選択のやり直し等）という現象自体が原理的に発生しないため、本記録はその真の検証にはなっていない。あくまで**参考情報**に留まる。
> - 本記録で確認できるのは「品質重視の選択」と「特性重視の選択」が**構造的に異なる結果を生む組み合わせが実在するか**（＝判断の分岐点・選択肢の対立構造が成立しているか）という、迷いの前提条件の一部のみである。
> - 正式な人間によるプレイテスト（検証対象者2〜3名以上、TASK-0010完了条件）は**別途実施が必要**。本記録はその代替ではなく、実施前の事前確認・手順の下地として位置づける。
> - 以下の記録は実際にGodotプロジェクト上でプロトタイプ（`alchemy_prototype.tscn`）を操作して得られた結果のみを記載しており、虚偽・誇張、実在しない人物の反応の記載は一切行っていない。

## 1. プレイテスト実施手順（人間の検証対象者向け）

TASK-0009で実装した1画面プロトタイプ（`atelier-godot/features/prototype/ui/alchemy_prototype.tscn`）を検証対象者に操作してもらう際の標準手順。

### 1.1 事前準備

1. Godotエディタでプロジェクト（`atelier-godot/`）を開き、`alchemy_prototype.tscn`を実行する
2. 検証対象者へ事前に断っておくこと（TASK-0009注意事項準拠）:
   - 見た目・演出は作り込まれていない（ボタンとリストのみのプレースホルダーUI）
   - 見た目の評価ではなく「素材をどう選ぶか」の判断に集中してほしい旨を伝える
3. 検証対象者には事前に目的（「なぜこの素材を選んだか、後で軽く聞きます」）を伝えるかは検証方針次第（先入観を与えたくない場合は検証後に質問する）

### 1.2 タスク実施フロー

1. 「素材入手」ボタンを複数回押し、インベントリに素材を集めてもらう（目安5〜8個程度）
2. インベントリから投入枠（最大4枠）へ配置する素材を選んでもらう
   - この配置決定の瞬間の様子を観察する（下記1.3）
3. 「調合」ボタンを押し、完成品（品質・発現特性）を確認してもらう
4. 「なぜその素材を選んだか」を軽くヒアリングし、品質重視/特性重視のどちらを意識したか、あるいは意識していなかったかを言語化してもらう
5. 余裕があれば投入枠の組み合わせを変えて2〜3回試してもらう

### 1.3 観察ポイント（TC-501-H01）

- 投入枠に配置する素材を選ぶ際に**手が止まるか**（考える時間が発生するか）
- 一度配置した素材を**入れ替える（やり直す）行動**が発生するか
- ヒアリング時に「品質が高い方」と「特性が揃う方」を**比較検討した発言**があるか
- 逆に、単純に「一番強そうなもの」を機械的に選んで完了してしまうか（迷いなし＝NO判定の兆候）

### 1.4 記録すべき項目（検証対象者ごと）

| 項目 | 内容 |
|------|------|
| 検証対象者ID | 匿名（例: 検証者1、検証者2） |
| 迷いの有無 | YES / NO |
| 根拠 | 観察された行動・発言（具体的に） |
| 選択に要した時間の目安 | 秒単位の目安 |
| 品質/特性トレードオフの所感 | 意図通り機能しているか |
| プロトタイプの実装バグ（あれば） | 観察結果と分離して記載。必要ならIssue化 |

## 3. AI自己検証（擬似プレイテスト）記録

### 3.1 実施方法

人間の検証対象者が確保できないため、AIエージェントが以下の方法でプロトタイプを実際に操作し、「品質重視の選択」と「特性重視の選択」が構造的に異なる結果を生むかどうかを確認した。

- Godotをヘッドレスモードで起動し、一時実行スクリプトから`alchemy_prototype.tscn`をシーンツリーへ実際に追加（`add_child`）した
- ボタン押下時に呼ばれる内部処理（`_on_gather_button_pressed()` / `_on_add_to_slot_button_pressed()` / `_on_craft_button_pressed()`）をボタンクリックと同じ順序・同じ引数構造で直接呼び出し、UIの状態遷移（インベントリ→投入枠→完成品表示）を実際に経由させた
- `PrototypeAlchemyResolver.resolve()`を単体で呼ぶのではなく、UI層を含めてプロトタイプ全体を動作させた点で、TASK-0009のGUTユニットテスト（Resolver単体10/10件）とは異なる検証範囲である
- 実行コマンド:
  ```bash
  Godot_v4.7-stable_win64_console.exe --headless --path . -s res://_task0010_playtest_sim.gd
  ```
- 一時スクリプトは実行後に削除済み（TASK-0009の`_scene_check.gd`と同じ運用方針）

### 3.2 検証パターンと結果

いずれもインベントリに8種類の素材（`PrototypeMaterialDefinitions.MATERIALS`全種）を入手した状態から、投入枠4枠に指定の組み合わせを配置し「調合」を実行した。

| パターン | 選択方針 | 投入素材（品質・特性） | 実行結果 |
|---------|---------|----------------------|---------|
| A: 品質最優先 | 特性のペア成立を無視し、品質の高い素材のみを選ぶ | 純水晶(S,なし) / 月の雫(S,contribution_purify) / 稀石(A,reward_rare) / 金粉(B,reward_gold) ※各特性は1個のみで発現閾値未満 | **品質A / 発現特性: 特性なし** |
| B: 特性発現優先 | 品質を犠牲にしてでも同一特性を2個揃える | 聖なる薬草(D,contribution_holy) / 清めの実(C,contribution_holy) / 黄金鉱石(D,reward_gold) / 金粉(B,reward_gold) | **品質D / 発現特性: contribution_holy, reward_gold** |
| C: 拮抗（中間） | 品質の高い素材1組と、特性ペアが完成する素材1組を混在させる | 純水晶(S,なし) / 月の雫(S,contribution_purify) / 聖なる薬草(D,contribution_holy) / 清めの実(C,contribution_holy) | **品質C / 発現特性: contribution_holy** |

### 3.3 構造的な観察（人間の「迷い」そのものではない点に注意）

- パターンA（品質のみ追求）とパターンB（特性のみ追求）とで、完成品の品質評価が **A → D** まで大きく変動し、かつ発現特性の有無も **なし → 2個** と対極の結果になった。これは「品質を取るか、特性を取るか」という選択が実際に異なる結果を生む——すなわち**選択肢が構造的に対立している**ことを示す。
- パターンC（中間的な選択）では品質C・特性1個という、AとBの中間的な結果が得られた。これは「全部は取れない」トレードオフの中で部分的に妥協する選択肢も存在することを示している。
- 上記は「選択の分岐点が構造として存在すること」の確認に留まり、「人間がその分岐点で実際に手を止めて考えるか」という認知的な反応（TC-501-H01が本来問うもの）は、この自己検証では**確認できていない**。特に、対立構造の存在は迷いの必要条件ではあるが十分条件ではない（対立があっても人間が直感的に即決する可能性は残る）。

### 3.4 発見した実装上の問題

なし。3パターンとも設計通りに動作し、コンソールにエラー出力はなかった（スクリプトエラーはフレーム待機の調整前の試行錯誤時のみで、最終実行では発生していない）。
